# Debug Report: EI-389 (Hive-Canary Missed Deadline)

## Failing assertion

Work item EI-389: Daily canary feature F-CANARY-20260611 in harness `hive-canary` never reached a terminal state within its 6-hour deadline. The DBOS routines engine died from 05:30Z to ~10:30Z due to an ESM `__dirname` incident. Diagnosis: why did the hive-canary routine fail to fire for this harness, and did recovery correctly reseed routines?

## Timeline & forensics

### DBOS engine outage (05:30Z — 10:37:53Z)

- **05:30Z**: Deployed code with bare `__dirname` in `packages/operator-core/lib/harness/routines/change-ledger-scan-action.ts` (line: `const REPO_ROOT = join(__dirname, '../../../../..');`)
- **05:30Z — 10:30Z**: DBOS routines engine dead. The import chain was poisoned: `register-system-actions.ts` (line 169) imports `change-ledger-scan-action`, which threw at import time under `tsx file-mode` (true ESM in type:module package), preventing every `system:<action>` handler from registering, including `system:hive-canary`.
- **~10:30Z**: Manual recovery attempted (per agent-insights runbook): git-sync sweep, green-checkpoint, deploy-cli.
- **10:37:53Z**: Fix applied via git-sync auto-commit (commit 321cfcb64, Fri Jun 12 06:37:53 2026 -0400 = 10:37:53 UTC). The file was corrected to use ESM-safe pattern: `const REPO_ROOT = join(dirname(fileURLToPath(import.meta.url)), '../../../../..');`

**Key finding**: Recovery at ~10:30Z preceded the fix by ~7+ minutes. At recovery time, the code was STILL broken.

### What happened during the window (05:30Z — 10:37:53Z)

1. **Register-system-actions import fails** — change-ledger-scan-action's bare `__dirname` throws at import, chain breaks before hive-canary is registered.
2. **DBOS engine fails to start** — the import failure is swallowed in the boot try/catch (`[dbos] boot failed (non-fatal): __dirname is not defined`), leaving the routines engine dead.
3. **Hive-canary routine exists in DB but is never dispatched** — the routine row exists in `harness_shared.routines`, but the tick loop never fires it because the engine is dead.
4. **Manual recovery at ~10:30Z fails to fix the engine** — the fix is not yet in the tree; the recovery process (git-sync, deploy) redeploys the same broken code.
5. **Fix arrives at 10:37:53Z** — the `:3070` restart (post-fix deploy) loads the corrected change-ledger-scan-action, the import chain succeeds, and DBOS boots successfully.
6. **Hive-canary routine fires immediately after recovery** — the routine was due (its `next_fire_at` was set to `now()` when seeded, long before 10:37:53Z), so the first tick after 10:37:53Z should have fired it.

### Hive-canary action behavior (when firing)

The action performs two phases:
1. **CHECK**: scan for overdue canaries (created > 6h ago, not terminal, not yet reported), gather forensics, file improvements.
2. **QUEUE**: insert today's `F-CANARY-<YYYYMMDD>` (idempotent).

The forensics collected (lines 121–130 of hive-canary-action.ts) queries:
- `dbos.workflow_status` — DBOS pipelines that should have processed the canary
- `harness_shared.spawned_agents` — nursery spawns (role fires)
- `harness_shared.autoloop_state` — role-based fire-state (link 1)

The output "no autoloop_state rows — the trigger chain (link 1) never fired" means NO role-based automations fired for the hive-canary harness.

## First divergence

The expected flow:
1. Hive-canary routine fires daily at 09:00 UTC
2. Phase 2: today's canary feature is inserted into harness_shared.work_items / harness_shared.harness_features_consolidated with status='todo', payload.canary=true
3. Upstream dispatcher (blueprint-run or equivalent) reads the todo canary feature
4. Dispatcher spawns scoper/worker/validator agents
5. Agents process the feature → terminal state (passed/failed/deprecated)

Actual observed:
1. Routine didn't fire at 09:00 UTC (05:30Z onwards — engine dead)
2. Routine may have fired AFTER recovery (10:37:53Z+), but forensics show "no autoloop_state rows"
3. Canary feature F-CANARY-20260611 either:
   - Was created before engine died (then dispatcher was also dead and never processed it), OR
   - Was created after engine recovered (then the 6-hour deadline may have already elapsed if checked on the next day's tick)

The specific divergence: the automation layer (autoloop_state, blueprint-run dispatch) shows ZERO activity for this harness. Either the blueprint wasn't triggered, or the trigger never recorded its state.

## Hypotheses (ranked)

### 1. **Hive-canary routine never fired during the outage, but fired correctly after recovery at 10:37:53Z** (65% confidence)

**Reasoning**: 
- The engine was dead 05:30–10:37:53Z, so the routine couldn't fire at 09:00Z.
- At 10:37:53Z the fix was deployed, DBOS recovered, and the routine was due.
- The first tick after 10:37:53Z should have fired it, creating today's canary feature.
- The forensics "no autoloop_state rows" refers to the hive-canary harness having NO role-based automations firing, which is expected if the harness has NO configured role routines (only the system:hive-canary routine).

**Test run**: 
- Query `harness_shared.routines WHERE install_slug = 'hive-canary'` to confirm the routine row exists and `active=true`.
- Query the `last_fired_at` column to confirm it was fired AFTER 10:37:53Z (e.g., between 10:38–10:45Z).
- Query `harness_shared.work_items WHERE harness_slug = 'hive-canary' AND feature_id = 'F-CANARY-20260611'` to confirm the canary feature exists with status 'todo'.

**If confirmed**: The routine fired correctly after recovery. The problem is NOT the routine; it's that the canary feature was queued but never processed (dispatcher/autoloop didn't pick it up).

### 2. **The recovery process at ~10:30Z partially failed, leaving the routine seeding/boot hook incomplete** (35% confidence)

**Reasoning**:
- The manual recovery at ~10:30Z (git-sync, green-checkpoint, deploy) follows the runbook steps, but the deployed code was still broken.
- It's possible the recovery process seeded the routine (via a boot hook) but with an incorrect `next_fire_at` (e.g., tomorrow instead of now), or the seeding never completed due to a partial failure.
- Or the routine was seeded BEFORE the outage, but its `next_fire_at` was advanced past the deadline window during recovery, preventing it from firing.

**Test run**:
- Check git-sync logs / operator journal entries between 10:25–10:40Z to see if the recovery steps completed.
- Check the `next_fire_at` value of the hive-canary routine — if it's set to tomorrow (2026-06-13) instead of today, the routine won't fire today.
- Check `harness_shared.routines.metadata` for any error messages recorded during recovery.

**If confirmed**: The routine seeding/boot was incomplete or misconfigured during recovery.

### 3. **The hive-canary routine's system action was NOT re-registered after recovery** (20% confidence)

**Reasoning**:
- Even if the routine row exists and its `next_fire_at` allows firing, the dispatcher must find the handler via `getSystemAction('hive-canary')`.
- If the recovery process did NOT restart the DBOS engine cleanly, the handler might not be registered.
- However, the fix in the code is already applied by 10:37:53Z, so a clean restart SHOULD register it.

**Test run**:
- Check if there are any `[routines] no handler registered for system:hive-canary` warnings in the `:3070` journal after 10:37:53Z.
- If the handler was missing, there would be a warning in the routines-workflow step and the action would be skipped with a reason.

**If confirmed**: The engine recovered but the handler registration failed.

## Ruled out

- **Canary harness not registered**: The forensics were gathered (Phase 1 of the action ran), which means the harness IS registered (the self-gate at hive-canary-action.ts:145 passed).
- **Routine row never seeded**: The routine must have been seeded (otherwise it wouldn't be in the work queue as "EI-389").
- **DBOS engine permanently broken after fix**: By 10:37:53Z the fix was in place, the engine restarted, and subsequent deploys/ticks should have succeeded (evidenced by other system actions firing since then, unless the whole engine is wedged).
