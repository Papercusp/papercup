This replaces the one-time ledger seed.\n- **Watch the blocker share.** If blockers grow past a set share of the suite, flake exposure comes back, so alarm on it.\n\n### Superseded proposal (kept for the record): who decides which failures are acceptable\n- **Day to day, nobody decides; the rule does.** The ledger is measured, never authored. It is exactly the set of tests failing on main, and it can only shrink. A failure that is not on the ledger blocks promotion. No agent can add an entry.\n- **The only human decision is the one-time seed,** made by the owner, from an explicit list. Guidance for admitting an entry to the seed:\n  - (a) It fails reproducibly on the candidate. A flaky test goes to quarantine instead.\n  - (b) It is not in a release-blocking area.\n  - (c) It has an owner and a work-item.\n  - (d) Shipping it to :3070 does not break something the fleet relies on there today.\n- **Release-blocking areas (never ledger-eligible):** DB migrations and schema; auth, permissions and secrets; data integrity or loss; deploy, rollback and release; build/typecheck of shipped code; the agent control plane (coordination, locks, work-items, MCP dispatch); and the gate itself.\n- **Leaving the ledger:** an entry leaves automatically when the test passes on a promoted candidate. Deleting or skipping a ledgered test needs a recorded reason on its work-item and appears in the daily digest. An entry older than 3 days escalates to its owner's lead and then the owner.\n- **Granularity:** entries are per test case where the runner reports one. A new failing case in an already-ledgered file counts as a NEW failure.\n\n## Rules in brief (labels R1–R10 used in item text)\n- R1 Every test blocks main by default (D-002). Nothing needs declaring. A test is non-blocking only through a recorded downgrade, or when written as non-blocking in an allowed class (perf, LLM scenarios). Gate legs (typecheck, lint, build) follow the same default.\n- R2 Promotion rule: main advances only when no blocking test fails on the candidate, so main is green on every blocking test at every promotion.\n- R3 Downgrade record (the override store): test (per file, with a per-case override where the runner reports cases), written reason, owner, filed bug, author and timestamp. A downgrade shows a warning, appears in the daily digest, and is undone by deleting the record.\n- R10 Downgrade guardrails: (a) the response to a blocking failure is fix, then eject (R5), then downgrade; (b) a downgrade of a test in the critical-area registry (migrations/schema, auth/permissions/secrets, data integrity, deploy/rollback/release, typecheck/build of shipped code, the agent control plane, the gate itself) is allowed with a forceful warning: an explicit acknowledgement naming the area and risk, and an immediate owner notice (D-006); (c) every downgrade is digested and counted (R7).\n- R4 Admission ratchet: an admission advances a repair head only if it adds no failure that was absent at the previous head, measured over the admission's radius. Otherwise it is rejected with the attributed tests named.\n- R5 New-red ejection: a new failure attributed to a specific commit removes that commit from the candidate, re-tests the affected radius, and routes the red to the commit's author. Before ejecting, the failing test is re-run on the base without that commit; if it fails there too, the commit is not the cause and the failure is unattributable (D-003). Only an unattributable failure freezes the candidate, until it is fixed or downgraded under R10.\n- R6 Determinism: a test whose verdict differs on the same commit goes automatically to an owned quarantine and stops counting. Round counts are compared only over the same measured population.\n- R7 Metrics and alarm: downgraded tests currently failing, downgrades per day, and new failures introduced vs. fixed per day. A rubric check alarms when downgrades or downgraded-failing debt grow, or introductions exceed fixes over 24h.\n- R8 The source-side sync-batch check runs on reserved capacity, so host load cannot skip it.
