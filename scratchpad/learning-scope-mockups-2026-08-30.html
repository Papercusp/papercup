Which pots are we
learning on?

There is no answer to that question anywhere in the product today — not because the setting is missing, but because it is split across four surfaces and organised by mechanism instead of by pot. Here is what actually exists, and the two controls that would fix it: a scope rail for picking the pots, and a pot drawer for tuning one.

Asked by Avi Workspace papercusp-workspace Evidence live DB + source, verified Tracking WI-1329910

The short answer

You can configure it — but not from the Learning tab, and never in one place. The Learning tab's pot picker is a view lens only (it filters what you're looking at; it changes nothing about what runs), and its header pause button is workspace-wide — it holds the whole self-improvement routine group, all pots at once.

The real switches live in three other places, one per mechanism: gym autoloops and governor lanes in the left sidebar's Arming section, Scout schedules in the Workflows tab, and Scout's per-pot tuning in Settings → Pot customization as raw JSON textareas. Nothing anywhere pivots that by pot, so "which pots are we learning on" cannot currently be read off a screen — I had to assemble it with SQL.

Where the switches actually are

Six controls, four surfaces, zero of them on the Learning tab

Each learning lane ships its own gate, and each gate got a home next to the mechanism that reads it. That is a defensible way to build it and an impossible way to operate it — the owner-facing unit is the pot, and no surface is organised that way.

What that costs, measured

Four things going wrong right now because of it

Every one of these is live in papercusp-workspace today, and each is invisible on the current surfaces.

The arming list is full of pots that no longer exist

The Arming section renders one row per gym_autoloop_config row, and that table is never garbage-collected. The registry knows about 27 hives; the arming list shows 53, and 28 of those name a pot the registry has never heard of — almost all of them throwaway benchmark harnesses.

registry hives 27 gym_arm rows 53 └ no such pot 28 (25 are xbench-* / xbh* / xbq*)

papercusp's gym is armed but cannot run

Its two gating layers disagree: the governor row carries a $50 lifetime budget, the autoloop config carries none — and an unbudgeted config is deliberately ineligible for the unattended path. This is exactly the drift gym:arm was built to prevent, and no screen shows the two layers side by side.

gym_autoloop_config enabled=true budget=NULL learning_governor enabled=true budget=$50 → tick refuses: unbudgeted

A per-cycle cap is rendered as a lifetime overrun

blender:papercusp is a per-cycle budget — $5 per run — against $513.82 accumulated across many runs. The Arming pane's money label has no idea, so it prints the two different units as one fraction, and the row reads like a 100× breach that isn't.

budget_kind=per-cycle enforcement=native armBudgetLabel(513.82, 5) → "$514 of $5"

The Learning tab's own "Open Arming" button doesn't open Arming

Three empty-states on the Learning tab offer an Open Arming action. It routes to tab=workflows&wfKind=routine — the routine schedule list. The Arming section with the actual spend gates is in the left sidebar, and the button never goes there.

useOpenArming() → { tab:'workflows', wfKind:'routine' } Arming lives in → AutomationPane (left sidebar)
The idea behind both mockups

Don't add a setting — transpose the one you have

Almost nothing below needs a new write path. Every value already sits in automation.catalog, and every lane already has an audited tool — gym:arm, governor:arm, routines:set. Most of the proposal is a pivot: the same rows, keyed by pot instead of by mechanism, surfaced where you already go to look at learning.

Both use one atom, so they compose rather than compete — a lane switch carrying its own state, budget and enforcement in a single glanceable chip:

The one thing that genuinely doesn't exist yet

A pot-level on/off — and it has to be a real gate, not a bulk write

You're right that neither mockup had this. Both showed lane switches; neither had "this pot is learning / this pot is not" as a control of its own — which is the actual question you started with. It is also the only piece here that has no existing switch to pivot, because today "is this pot learning" is merely derived from whether any lane happens to be armed.

That derivation is why a master toggle can't just be a bulk write. If turning a pot off means writing enabled:false across its lanes, turning it back on has no idea which ones were on — and it would silently revive a lane you had deliberately parked. There are two honest ways to build it:

  • A real gate. One stored per-pot flag every lane's preflight checks, on top of its own arming. Off means off no matter what an agent writes underneath; each lane keeps its own config untouched, so on/off is perfectly lossless. Costs a migration and a line in each preflight.
  • A remembered bulk write. No new gate: turning a pot off writes its lanes off and stamps each row with who held it, so resume restores exactly what the pause held and never revives a deliberate pre-existing hold. This is not a new idea — it is precisely what routines:group-set already does for the self-improvement group, so the semantics are proven here. Cheaper, but an agent calling gym:arm can still re-arm a pot you switched off.

The mockups below draw the gate version, because the whole point of this control is spend safety and the second option leaves a hole an autonomous agent can walk through. It is a real fork though, and it's yours — I've asked it below.

Mockup B — Scope matrix  ·  cut

The proposed third screen was a full pots × lanes grid on its own lview=scope pane. Owner call, 2026-08-30: it doesn't earn its place next to A and C — and that's right. Its only capability neither of the others had was bulk operations across pots, and A's scope picker now does that with checkboxes at a fraction of the cost.

Everything else it offered was a second, heavier rendering of data A already carries: the per-pot lane state is in the rail chips, the per-pot detail is in the drawer, and the orphan-row cleanup is one fold in the picker — better still, a teardown at pot-dissolve means those rows never accumulate to be cleaned up.

Pot learning drawer

One pot's complete learning configuration in a drawer, opened from a rail chip or the pot selector. The plan

A, then C

  1. The pot gate first — one stored per-pot learning flag, checked by every lane's preflight. It is the smallest piece and everything else reads or writes it, so it lands before either screen.
  2. Then A: the rail, the popover, and the scope picker. This is the whole of "which pots are we learning on, and change it" — and it retargets the three Open Arming buttons, fixing the one that currently lands on the wrong screen.
  3. Then C, the per-pot drawer, once A tells us which knobs anyone actually turns. Building it first would mean hand-authoring fields for JSON we may find nobody edits.

Two fixes are worth doing regardless and cost almost nothing: teach the money label to read budget_kind so a per-cycle cap stops rendering as an overrun, and give gym_autoloop_config the teardown at pot-dissolve that would have kept 28 dead rows off the list.
