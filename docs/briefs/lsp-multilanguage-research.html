Code intelligence WI-40244 2026-08-21

Beyond TypeScript and Rust

Supporting every language out of the box for public users — what it costs, how our own wrapper compares to Serena and the field, and the two risks that only appear once you ship.

Requirement changed mid-analysis

This page was first written against "we need TS and Rust, maybe Python and Bash." The requirement is now public release, all languages out of the box. That falsifies the original Q4 conclusion — "a fifty-language maintenance surface is a bad trade for two" — and it is rewritten below rather than patched. Two findings survive unchanged; one recommendation reverses.

The short answer

The LSP plumbing is not the cost. The provisioning matrix is — and at public scale that matrix is the product. Every project here, Serena included, converges on the same thin protocol client; what separates them is operational knowledge about how ~300 servers install, version, and boot.

Do not hand-author all of it — but do not believe you can consume all of it either. mason-registry publishes its whole package set as a checksummed, version-pinnable registry.json release, and I have now downloaded one and attempted the mapping rather than reasoning from its documented shape. The result, measured: mason carries 100% of the provisioning and licensing data and 0% of the protocol contract — no languageId, no launch argv, no readiness semantics. Joining its declared neovim.lspconfig key to nvim-lspconfig recovers most of the rest, giving 74.2% derivable as pure data — but the missing quarter is disproportionately the popular languages, TypeScript included. Two sources plus a hand-authored tier for the residue; see the update box at the end.

Keep our own wrapper — D-002 still holds, and for a reason that got stronger: our adapter is the only thing in this field that refuses to answer while a server is still indexing. At two languages that was a nicety. At three hundred, where most servers you have never tested, it is the difference between a product and a liar.

Q1

How we would add another language

Today it is a code change, not a config change — and it carries a trap worth fixing before anyone attempts it.

✓ verified in our code packages/operator-core/lib/code-intelligence/lsp-adapter.ts 
export type LspLanguage = 'typescript' | 'rust';        // closed union of two

resolveServerBin(language) {
  if (language === 'typescript') { ...vendor/.bin/typescript-language-server }
  // no else-if, no switch — FALLS THROUGH to:
  return ~/.rustup/.../bin/rust-analyzer
}

languageId: client.language === 'typescript' ? 'typescript' : 'rust'   // :616
languageId: client.language === 'typescript' ? 'typescript' : 'rust'   // :1143
The trap

The two-language assumption is expressed as if typescript … else RUST in at least three places. Add 'python' to that union and it compiles clean, then hands you rust-analyzer labelled as Rust. Because there is no switch, TypeScript's exhaustiveness checking cannot catch it — the failure is silent and runtime-only.

So the first step is not "add Python." It is converting language from a union-plus-branches into a declared spec. We already have the pattern in the same file — REQUIRES_PROGRESS_SIGNAL is a per-language Set, which is exactly the data-driven shape the rest should follow.

The second problem: our intent matrix has holes already

✓ verified in our code contracts.ts · lsp-adapter.ts 
CodeIntelIntent  = 9 declared
  definition · references · implementations · callers · callees
  impact · rename-preview · diagnostics · symbol-search

METHOD_BY_INTENT: Partial<Record<CodeIntelIntent, string>> = {
  definition:      'textDocument/definition',
  references:      'textDocument/references',
  implementations: 'textDocument/implementation',
}                                              // 3 of 9 wired

grep -c 'capabilit|unsupported' contracts.ts → 0   // no per-language declaration

Nine intents declared, three wired, and no place to say which language answers which intent. That is survivable at two languages where the answer is uniform. It stops being survivable the moment the matrix becomes ragged — and the research says it becomes ragged immediately (see Q2).

The cost ladder

Done

Make LanguageSpec data WI-40250 shipped

One record per language, behind a Record<LspLanguage, LanguageSpec> — exhaustive by construction, so widening the union without adding a spec is now a compile error. All three else-is-rust sites are gone and an unknown language throws instead of resolving to someone else's server. 13 tests pass, lint:tsc clean.

Next

Open the registry — closed union → tiered

All-languages needs an open registry, which is in tension with the closed union above. Resolve it by tiering rather than abandoning: a closed, exhaustive union for verified languages, plus a data-driven registry for the long tail. A generic LSP client can drive any stdio server; only the spec varies.

Next

Declare capability per intent, per language

An explicit matrix cell: answered, unsupported by this server, or not yet wired. Optional at two uniform languages. Mandatory at three hundred, where you cannot have tested most cells — this is what stops an untested cell from rendering "cannot" as "none."

The product

Provisioning + licensing at public scale

No longer a maintenance footnote — it is the bulk of the work and the only part with legal exposure. Consume mason-registry rather than authoring it; fetch at runtime rather than bundling. See §5.

Q2

How the options compare

Four architectures are genuinely distinct here. They differ less on what they can answer than on what they cost to keep alive and how they fail.

Architecture Truth source Freshness Cost shape Fails as
Our adapter current Official pinned servers Live, incl. uncommitted edits One warm process per language False-empty during warmup mitigated
Serena / SolidLSP Same servers, via its own client Live Separate Python service + its deps Same false-empty class
Index (SCIP / LSIF) Precomputed index Stale the moment you edit Batch indexing job Confidently out-of-date
Tree-sitter graph Parse tree, no type resolution Cheap to refresh Index build Syntactic guesses at semantic questions

Two things follow that are directly relevant to us.

The fourth row is already ours. GitNexus is our tree-sitter-shaped layer, which means we are not choosing between LSP and a graph — we are running both and routing between them. D-001's authority table is exactly that routing decision, and it is already shipped.

"Supported" does not mean "answers your intents." This is the finding I would most want on the record, because it changes the shape of the work rather than its size.

From Serena's own language table

Crystal has no find-references. HLSL has no reference search. Wolfram's references are file-local only. The Ansible server ships without document symbols, workspace symbols, references, or rename. Kotlin's server is pre-alpha; Erlang is flagged as possibly hanging.

These are languages on the supported list. Breadth counts languages; it does not count answered questions.

Serena's 30–50 language claim is real, but it is a count of adapters, not a guarantee across our nine intents. Any multi-language plan we adopt has to model that raggedness explicitly — which is precisely the medium rung above, and it is a requirement we would not have derived without looking at their table.

Q3

What actually competes with Serena

Yes — several projects, though the field is thinner than the search volume suggests. Most top results for "Serena alternative" are forks of Serena. These are the genuinely independent ones.

Project Lang Shape Notable Maturity
isaacphi/mcp-language-server Go One process per (workspace, server) 6 tools. Config is pure CLI args — no plugin system at all beta
Token Saver MCP TS VSCode extension + MCP server 31 tools incl. browser control; needs VSCode running niche
karellen-lsp-mcp Py Shared daemon, refcounted servers Refcounting is the fleet-economics answer — see below early
mickeyinfoshan/lsp-mcp Go Sessions keyed by (language, root) gopls, tsserver, pylsp early
ProfessioneIT/lsp-mcp-server TS Claude Code-focused Adds call + type hierarchy — the callers/callees we left unwired early
microsoft/multilspy Py Library, not a server The substrate Serena forked into SolidLSP research

Three things worth stealing

karellen's refcounted shared daemon independently arrives at D-002's rationale #5 — thirty concurrent agents cannot each run tsserver, so any winner must be one warm shared instance. That someone else converged on it is meaningful corroboration of a call we made on reasoning alone.

nvim-lspconfig holds roughly 300 server configurations as data, with Mason as a parallel provisioning registry and a hand-maintained translation table joining them. That is the mature shape of the registry problem, and it is the pattern our LanguageSpec should imitate rather than reinvent. confirmed by the spike — this paragraph turned out to be the load-bearing one. The two-registry split is not an implementation detail of Neovim's ecosystem; it is forced, because provisioning data and protocol data have different owners and neither registry carries the other's half. We should copy the split, not just the contents.

isaacphi's config model is a real design position, not an omission: no plugin system, no registration step — you install a binary and name it on the command line. It is the cheapest possible answer to Q1, and it works because it pushes provisioning entirely onto the operator.

What nobody has solved

None of these projects handles the failure that actually bit us. Every one returns whatever the server returns; a server that is still indexing returns an empty list, and an empty list renders as "no callers." We hit this in WI-40224 and built a readiness contract around it. That is the one place our wrapper is ahead of the field — which is also why adopting any of them would have been a step backwards on the axis we care about most.

Q4

What if we made our own wrapper?

We did. That is what D-002 chose and what lsp-adapter.ts is — 1,244 lines driving official pinned servers over vscode-jsonrpc. So the real question is not whether to build one, but what we would be signing up for at N languages.

The answer is visible in Serena's own documentation, and it is sobering. Their language table is not a list of names — it is fifty separate operational stories:

  • Runtime prerequisites that are not ours to control — Java 21+, .NET v10+, pwsh, opam, uv/uvx, elan with a prior lake build
  • Binaries auto-downloaded and SHA-256 verified, because supply chain is now your problem
  • Servers reached over TCP rather than stdio — Godot's is on port 6008, and Serena will not start Godot for you
  • A licensed MATLAB R2021b+ installation
  • Per-language quirks that leak into the API — Erlang addresses functions as name#arity because / is their name-path separator

None of that is protocol work. All of it is maintenance, and it recurs every time a server publishes a breaking release.

The reframe

Serena's moat is not its LSP client — it forked that from Microsoft's multilspy. Its moat is the accumulated per-language provisioning knowledge. And that knowledge is not merely public; for ~300 packages it is already machine-readable.

So the build-vs-buy question is malformed. The real axis is authored vs consumed: we keep our own client (buying one gains us nothing on truth) and consume someone else's registry (authoring one gains us nothing but toil).

What "all languages" actually costs

My earlier answer — that a fifty-language surface was a bad trade for two more languages — was correct for the old requirement and is now void. Under public release the arithmetic inverts, and three costs replace it:

  • Registry ingestion — pull registry.json.zip + checksums.txt from a pinned mason-registry release, validate against its published JSON schema, map its purl source identifiers onto our LanguageSpec. Bounded, and it is a data pipeline rather than 300 hand-written adapters.
  • Runtime provisioning — download, verify, cache and version-pin a server on first use for a language we may never have run. Serena does exactly this, SHA-256 included, which tells you it is necessary rather than optional.
  • Honest degradation — the hard part, and the one nobody else does. With 300 languages you will ship cells you have never exercised, so the system must be able to say "this server does not answer that" and "this server is not ready yet" as first-class results, distinct from "there are none."

That third cost is the one that decides whether this is a product or a liability, and it is the one we are already ahead on.

Q5

The two risks that only appear once you ship

Neither of these existed while this was an internal tool for one repo. Both arrive with the public release, and the first is the kind that is expensive to discover late.

Licensing — process separation is the safe architecture

Shipping language servers to public users is a redistribution question, and the servers are not uniformly permissive. clangd is Apache-2.0 WITH LLVM-exception; rust-analyzer is dual MIT/Apache-2.0; pyright is MIT. Those bundle cleanly with attribution. But the long tail is not uniform — texlab is GPL-3.0, and Serena's own docs note it runs as a separate process, which is precisely the mitigation. Others are worse than GPL: Serena lists MATLAB requiring a licensed R2021b+ install, and Pylance is proprietary and licensed only for Microsoft's own editors.

measured by the spike The mason release quantifies this exactly, across its 325 LSP packages: MIT 203, Apache-2.0 70, then a real tail — 9 GPL-3.0-or-later, 9 GPL-3.0, 5 GPL-3.0-only, 9 MPL-2.0, 3 LGPL-2.1, 2 LGPL-3.0, 2 AGPL-3.0, 1 LicenseRef-Qt-Commercial, and 8 flagged outright proprietary. So roughly a tenth of the catalogue cannot be bundled on the same terms as the rest, and the licence field is machine-readable — which means the policy below can be enforced by the pipeline rather than remembered by a person.

The lever

Fetch at runtime; never bundle. If the product downloads the user's own copy from upstream on first use, you are arguably not redistributing at all — which sidesteps notice obligations entirely. Invoking even a GPL server as a separate process over a documented protocol is the standard argument against derivative-work status; bundling that same server in an installer is what triggers source-offer obligations.

An LSP adapter is already a separate-process architecture. That is a genuine strategic advantage of the D-002 design that had nothing to do with why we chose it.

Minimum viable compliance if we ever do bundle: a THIRD-PARTY-NOTICES file carrying each server's full license text and copyright headers, surfaced in-product, with a per-version manifest so the notices track what actually shipped. Flagging rather than deciding — this one wants a lawyer's eye, not an engineer's. (I am not one, and this is not advice.)

Supply chain — you are now an installer

Auto-downloading executables onto user machines makes us a distribution channel with the attendant obligations: pin to a dated registry release rather than "latest", verify checksums on every fetch, and make the provisioned set inspectable so a user can see exactly which binaries we placed on their disk and why. mason-registry ships checksums.txt alongside the registry precisely because this is a known hazard.

What I would actually do

Step 1 is done. The rest is ordered so that each step makes the next one safe:

  1. Fix the else-is-rust fallthrough — shipped as WI-40250. The three branch sites are now a Record-backed spec table; an unknown language throws instead of silently resolving to rust-analyzer. 13 tests, lint:tsc clean. Under the new requirement this was not optional housekeeping — arbitrary user languages would have hit that else arm constantly.
  2. Tier the registry. Keep the closed exhaustive union for verified languages; add an open, data-driven registry for the long tail. This is the one place the shipped fix needs deliberate extension rather than reuse.
  3. Add the per-intent capability matrix. Was "medium" under the old requirement; is load-bearing under the new one, because most cells will be untested. Never let "cannot" render as "none."
  4. Ingest mason-registry and nvim-lspconfig — pinned release, checksum-verified, schema-validated, mapped onto LanguageSpec. Corrected by the spike (see the update box below): this is a two-source pipeline, not one. Mason supplies provisioning and licensing; nvim-lspconfig supplies the protocol contract mason does not carry at all. Together they cover 74.2% as data — and the missing 26% is disproportionately the popular languages, so it needs a hand-authored third tier rather than being treated as a long tail. Still a data pipeline rather than 300 adapters, but roughly 84 of those adapters are real.
  5. Runtime provisioning with fetch-not-bundle — for the licensing reason in §5 as much as the size one. Get a lawyer's read before any bundling decision.
  6. Wire callers/callees via call hierarchy — we declare them and do not answer them.

What I would not do: adopt Serena. Not out of NIH — the reasoning has just inverted. Its value is the provisioning knowledge, and the machine-readable half of that is available without the dependency; meanwhile its one architectural weakness is the false-empty class, which is exactly the axis that gets more dangerous at 300 languages. We would be importing the liability and re-deriving the asset.

↻ Update — the spike has now been run, and it moved the answer

This box previously said the claim I most wanted challenged was that mason-registry's registry.json maps cleanly onto a LanguageSpec, and that I had not downloaded one to check. I have now done it — pinned release 2026-08-21-imaginary-beer, both published checksums verified, joined against nvim-lspconfig v2.11.0. The premise survives, but not in the shape I described, and the correction matters more than the confirmation.

Mason answers "how do I install this binary" and says nothing whatsoever about how to speak to it. Of the 325 LSP packages: provisioning recipe and licenses are 100% present, an executable declaration 98.2%. But languageId, the stdio launch argv, readiness semantics, and the capability matrix are 0% — every single field our LanguageSpec exists to carry. A generator fed only by mason would have produced the half we could have guessed and none of the half that is hard.

The recovery is real but is a second pinned source: mason declares a neovim.lspconfig join key, and nvim-lspconfig carries cmd and filetypes. That key resolves for 274/325 (84.3%; 9 dangle, 42 absent). Of those, cmd is static data for 92% — and a Lua function for 18 servers. Net: 241/325 = 74.2% derivable as pure data.

The sting is which 26% falls out. The function-cmd entries are not the long tail — they are typescript-language-server, tsgo, jdtls, eslint, json, html, css, yaml, tailwind, svelte, angular, astro, biome, ruby-lsp, csharp, powershell. Most of the web stack plus Java, Ruby and C#. And the reason is structural rather than accidental: cmd is a function precisely because those servers need per-project resolution (ts_ls prefers a project-local node_modules/.bin binary over a global one). The entries that need real logic are the entries that have real users — so 74.2% must never be quoted unweighted. Our own first language, typescript-language-server, is in the residue.

So step 4 below is re-scoped rather than cancelled, and a third tier — hand-authored specs for the ~84 residue servers, ordered by usage rather than alphabet — is now an explicit plan item that was missing before. Recorded as D-001 on plan lsp-fleet-scale-all-languages-2026-08-21, with the method caveat stated there: the static-vs-function split is a line-anchored regex over Lua source, not a Lua parse, so 74.2% is a floor.

The claim I would now most want challenged

That one warm server per (language, projectRoot) can actually absorb a thousand agents. Every number in the architecture above rests on sharing, and sharing rests on a saturation curve nobody has measured — an LSP server is effectively single-threaded, so the queue in front of it is the multiplexer. If the knee arrives at fifty concurrent queries rather than five hundred, replicas-by-shard stop being a contingency and become the design, and the memory arithmetic that ruled out per-agent servers has to be re-run against per-shard ones. That is the next spike, and it is the one that can still invalidate the shape.
