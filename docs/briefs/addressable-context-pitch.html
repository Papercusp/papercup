Addressable Context

Do agents need to run at the same time? Mostly no — and the "mostly" is worth building around. The decomposition of what concurrency actually buys, the primitives we shipped for each piece, and the retired-experts defense checked against the real autopsy.

"Why is concurrency better than serial, beyond speed?" decomposes into five distinct benefits with different requirements. Exactly one irreducibly requires simultaneity.

2The decomposition

  1. Speed — wall-clock. Conceded, boring; any parallel system has it.
  2. Bidirectional information flow in the decision timeline. Serially, discoveries flow only forward: agent 3's bug find can't reach agents 1–2, whose finished work is now wrong. Concurrently, any discovery course-corrects every peer mid-flight — and truncates the tokens peers would burn down invalidated paths. A cost argument, not just latency.
  3. Correlated observation of shared live state. N agents watching the same pipeline at the same moment run a controlled differential: same world-state, varying only platform. Commonality isolates shared causes; difference isolates platform causes.The only benefit that irreducibly requires simultaneity
  4. Pull-deliberation. Asking a question of the context best equipped to answer it, getting fresh reasoning back. Requires wakeability, not simultaneity. → consult:get_feedback, shipped.
  5. Push-interjection. A peer volunteering something you didn't know you needed. Requires interest subscriptions + wakes. → interest watches (watch:create), shipped.

Conceded for honesty: perspective diversity does not require concurrency — it requires independent contexts, which serial fresh sessions also give. We don't claim it.

Injection vs consult. Context injection is retrieval of what was already said — it can only answer questions the past agent happened to address. A consult is fresh reasoning applied to a novel question — a colleague, not a library. Every consult is persisted and backfills retrieval: the first ask costs a wake, repeats are served by injection. A cache hierarchy, not rivals.

3The pitch line

Concurrency isn't the feature — addressable context is. We decomposed what "working at the same time" actually buys and built each piece as a first-class primitive, so simultaneity becomes a performance knob rather than an architectural requirement. Live coordination is the zero-latency special case — and where simultaneity is genuinely irreducible (correlated observation of a live shared system), we run truly parallel.

4What we built — shipped, enforced, tested

Each guardrail is a server-enforced mechanism, never guidance prose:

  • Router: embed the question; search cross-agent turn history; blend similarity with recency, verification evidence, and authorship — similarity ≠ authority: the agent with the most turns on X may be the one most stuck on X.
  • Score floor + honest failure: below the floor, the first-class answer is "no qualified responder — proceed on your own judgment." Falsifiability-tested.
  • Requester tool: get_feedback({ question, tried, observed, decisionAtStake, latency }) — the prompt doubles as the embedding query; specificity is routing quality.
  • Responder contract: validate relevance first, decline cheaply; answer from transcript, citing evidence; the requester owns the decision.
  • Thread lifecycle: exchange cap; every message carries a question or a new fact (neither = structural close); recursion depth ≤ 2; cycle refusal; per-task wake budget; expiry sweep (live-verified). Cap-hit deliberation graduates into shared live work — full concurrency re-enters as the escalation tier, not the default posture.
  • Retrieval backfill: closed threads are indexed; repeat questions are served by injection, no wake.
  • Interest watches: standing interests wake an agent when a peer's in-flight work matches (similarity floor; frontier watermark over async-backfilled embeddings).

5.1 What the retired system actually was — recovered from git history

The referent is the experts system: authored persona experts, in two generations. Planning-pass experts — one expert per feature area authoring a SPEC.md, critiqued by ephemeral feedback agents from an authored persona roster (security, UX, perf, a11y, ops, implementer, domain-expert, devil's-advocate); convergence = two consecutive empty-issues verdicts; agent cap 12; cost budget. Direct-writing experts — autonomous specialist roles (first: infra-reviewer) defined by an authored prompt plus a hand-written whenUseful manifest telling the scoper when to consult. A directory of authored experts.

Timeline from file history (not commit subjects — those ride git-sync sweeps): docs removed 2026-05-20; the operator implementation — 22 files, −2,959 lines — removed 2026-06-03. Its whole operator life is measured in weeks.

5.2 The difference, in one line

The old system's experts were authored — a roster of persona prompts someone wrote. The new system's experts are discovered — histories earned by doing real work.

Authored roster — retiredDiscovered histories — shipped

5.3 The rot is observable in-tree, today

Live exhibit The current blueprint scoper.md (lines 44–65) still instructs the two-phase useExperts flow — telling the scoper to POST /api/harness/…/experts and read prompts/expert.md — against routes and prompts deleted 2026-06-03. The authored structure outlived its own substrate by two and a half months, silently. A system whose expert set is computed at query time has no such artifact to strand.

Honesty invariant (testable, tested): "no qualified responder" must be a common result in practice. If every call returns an answer, the floor is broken and these are costumed experts again.
