Both ends are finished. Calendar's POST /api/sync already upserts idempotently, records a cursor, and publishes a change event that drives the live UI. The platform already stamps email-message and calendar-event onto provider events before any app sees them. The two were simply never connected.

Why this matters now: the ship of email-calendar-web-desktop-ship-2026-08-27 was retracted over exactly this. Its acceptance criterion web-apps-real-data says not-met if either app's real-data path is only demonstrated against fixtures — and today the only callers of either ingress are a manual curl and a test.

Evidence

Four independent negatives

  • trigger_deliveries.sink_kind is only ever personal-vault, trigger-bindings, or event-bus. There is no app sink, ever.

  • Nothing in the platform posts to the apps — grep for api/sync returns one unrelated comment. No sync-target config exists.

  • Neither app reads the vault. Zero hits for personal_documents across both repos.

  • The apps call platform verbs outbound only. There is no read-back verb. (The data: string in platform.ts is SSE line-parsing, not a data verb — it looks like a pull path and isn't.)

Constraints discovered

Two asymmetries the design has to resolve

No cursor

Email has no batch ingress

Calendar has POST /api/sync with a cursor and status. Email has only POST /api/messages/ingest — one message, no watermark, nothing to resume from.

Fans out work

Email conflates content and judgment

Its /api/triggers/gmail stores the message and mints a work item. Backfilling 680 messages through that door would create 680 work items. Found the hard way: one documented smoke-journey curl minted WI-976558.

Design decisions

Five calls, and what each one rejects

D-001

A scheduled routine, not a new delivery sink

Chose

A tier:durable routine that reads canonical rows and POSTs batches to each app.

Rejected

Adding an app-ingress sink to the trigger-delivery path.

Why

A sink fires per-event and cannot backfill — the 708 rows already in the vault would never arrive, so the apps stay empty until new mail happens to land. The apps' contract is batch + cursor, which a per-event sink can't express. Repo convention also allows exactly two mechanisms for recurring work and forbids inventing a third. Keeping delivery decoupled means an app being down can't wedge the pipeline that also feeds the vault.

Cost

Latency is one interval, not real-time. A push sink can layer on later as an optimization — not instead of this.

D-002

The app owns its watermark; the producer asks

Chose

Each run calls the app's GET /api/sync/cursor and sends from there.

Rejected

A producer-side watermark table.

Why

A producer-side watermark silently desyncs whenever an app's store is reset or re-provisioned: the producer believes it already delivered rows the app no longer has, and the app stays permanently short with nothing failing loudly. Asking the receiver is self-healing — a wiped app reports an empty cursor and refills itself. One fact, one source of truth.

D-003

Content sync never uses the judgment door

Chose

Sync targets content-only endpoints. The judgment plane keeps its own path.

Rejected

Reusing /api/triggers/gmail because it already accepts canonical payloads.

Why

It would mint one work item per message — 680 on backfill. The rule this sets: an endpoint that both stores content and triggers judgment is not a sync endpoint. Keep the two separable at the API boundary so bulk content movement can never fan out agent work.

D-004

Read the canonical store, not the delivery log

Chose

personal_documents — canonical and deduped.

Rejected

trigger_deliveries.

Why

The delivery log holds one row per sink per event — 2040 rows for 680 actual messages. Consuming it would deliver each message about three times and make correctness depend on sink fan-out that has nothing to do with app content. Note for auditors: the "135 calendar-event rows" a prior grading cited as real-data evidence is a delivery-log count, not anything either app received.

D-005

Email gains a batch ingress mirroring Calendar's

Chose

POST /api/sync on Email taking { messages[], contacts[], cursor?, sourceRef? }.

Rejected

Looping the singular endpoint 680 times.

Why

No cursor means no watermark to resume from (breaking D-002) and no status to record; a 680-request backfill has no reporting boundary, so a failure halfway leaves the app in a state nobody can describe. Two apps consuming one generic system should present the same ingress contract, or every future consumer special-cases them. It wraps the existing idempotent ingest rather than reimplementing it.

Plan · platform-to-app-data-producer-2026-08-30

Nine items, three phases

Phases are a real sequence, not decoration: the producer in Phase 2 cannot be written until Phase 1 settles the contract it posts into.

ItemWork
Phase 1 — Close the contract asymmetry
P-001Batch + cursor ingress on Email: EmailSyncBatchSchema, POST /api/sync, GET /api/sync/cursor, /status. Wraps the existing idempotent ingest. Must not mint work items.
P-002Owner mapping: platform user_id → each app's ownerId. Explicit, never inferred — the apps scope every read by owner, so a wrong mapping delivers one person's mail into another's app.
P-003Service auth: short-lived JWTs per app audience, signed with the app's existing secret. The apps already verify exactly this — no new auth scheme.
Phase 2 — The producer
P-004The routine: per (owner, app), read the app's cursor, select rows after it, map to the batch schema, POST, record outcome. Idempotent by construction — both apps upsert by id.
P-005Backfill 708 existing rows through the same path as steady-state, in bounded pages. A separate importer is how the two silently diverge.
P-006Loud failure: per-app cursor, row counts, last error. A silently-idle producer is indistinguishable from today's broken state — which is the failure this plan exists to end.
Phase 3 — Prove it and re-ship
P-007The test WI-933686 asks for: real data through each app's own run path, asserted on the receiving end — a row in the app's store traced to a provider id — never on the sending abstraction.
P-008Correct calendar/TESTING.md §4, which describes this producer as already existing.
P-009Re-open acceptance: re-activate the retired rubric, non-implementer re-grades web-apps-real-data, fresh verdict, then re-ship.
Your call

Four questions I shouldn't decide alone

1 · How fresh does the data need to be?

D-001 buys backfill and simplicity at the cost of interval latency. A one-minute routine feels live for mail; if you want true real-time, that's a push sink layered on top and more moving parts.

2 · One owner, or multi-tenant now?

P-002 is much simpler if this is just your account. Building the mapping generally is the kind of thing that's cheap now and expensive to retrofit — but it's speculative if these apps stay personal.

3 · Backfill everything, or a recent window?

All 680 messages, or the last 30 days? Full backfill makes the app immediately useful; a window gets you there faster and avoids importing years of noise you'd never open.

4 · Should Email's trigger endpoint keep firing judgment?

D-003 routes around the conflation rather than fixing it. Splitting content from judgment properly is the cleaner design, but it touches a path that currently works.
