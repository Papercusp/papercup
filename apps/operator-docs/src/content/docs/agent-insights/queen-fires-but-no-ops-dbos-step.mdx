## Symptom

The autonomous Queen (the `hive` autoloop) fires every ~30 min, but
`harness_shared.spawned_agents` rows with `child_role='queen'` show `duration_ms`
of 19-80 ms with `status='done'` (a real Queen turn is ~20 s). The fleet stays
empty — no work-items created, no bees placed — and `hive:status` shows
`fires24h` ≈ 48-52 (pure 30-min watchdog fallback, never a demand wake).

## Root cause

On the **green `:3070` operator** the env carries `PAPERCUSP_DBOS_ROUTINES=1` and,
unlike staging, **no** `PAPERCUSP_DBOS_AUTOLOOP=0` / `PAPERCUSP_BACKGROUND_WORKERS=0`
guard. So the hive autoloop runs *inside a DBOS step/transaction*, and when it fires
the Queen via `durableSpawnFire` (`launch-blueprint.ts` → `defaultFire`), DBOS
rejects it:

```
[durable-spawn] could not enqueue durable fire (papercup-hive/queen); falling
back to fire-and-forget: Invalid call to a `workflow` function from within a
`step` or `transaction`
[blueprint-run] papercup-hive: fired launch blueprint 'hive' (role queen)
[invoke papercup-hive] hive turn finished with no next wake armed
```

The durable enqueue fails → falls back to fire-and-forget → and the turn
"finishes" in the same second (the 19-80 ms no-op), arming no next wake. So the
Queen never actually runs an LLM turn: she places nothing and is not the gateway's
fault (it reproduces with the gateway healthy).

## Confirm it

```
journalctl --user -u papercup-dev-api --since "30 min ago" \
  | grep -E "durable-spawn|hive turn finished"
```

The `workflow function from within a step` line + a same-second `hive turn
finished with no next wake armed` is the signature. Cross-check
`spawned_agents` `child_role='queen'` rows with `duration_ms < 100`.

## Fix directions

1. **Proper fix:** fire the Queen **outside** the autoloop's DBOS step — defer the
   launch until after the step commits, or use a DBOS-step-safe enqueue
   (`DBOS.startWorkflow` from the right context) instead of calling a workflow
   function from inside the step.
2. Make the fire-and-forget fallback actually run the turn — today it no-ops under
   the broken context, so even the fallback doesn't recover the Queen.
3. **Config workaround (not a real fix):** guard the autoloop off under DBOS on
   `:3070` (set `PAPERCUSP_DBOS_AUTOLOOP=0` like staging). Needs a `:3070` restart
   and has side effects.
