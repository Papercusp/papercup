## What

A common (and load-bearing) misread: "the Hive Queen RESUMES her prior session
every wake (`claude --resume`), so she's a forever-session with an unbounded
growing transcript." **This is wrong.** Verify before designing on it.

The Queen's **declared, event, watchdog, and manual wakes are ALL already
fresh-per-wake** — each spawns a brand-new claude session with a fresh session
id and **no carried transcript**. The ONLY path that `--resume`s the Queen is
the *generic* wake-executor inbox/await delivery channel (a `coord:send` with
`wake:true` to her owner id, or an `events:await` she registered — which her
persona tells her not to use).

## The wake paths (all FRESH except one)

| Path | Trigger | Mechanism | Session |
|---|---|---|---|
| Time wake | `hive:declare-wake {inSeconds}` | `hive-wake` routine → DBOS routinesTick → `system:blueprint-run` → `fireLaunchBlueprint('hive')` → `POST /harness/:slug/invoke?bpkind=hive` | **FRESH** |
| Event wake | `hive:declare-wake {events}` | reaction rule → `hive:wake` tool → `fireLaunchBlueprint('hive')` → same invoke route | **FRESH** |
| Watchdog recovery | turn-end / boot / 30s tick (`watchdog.ts armFallbackHiveWake`) | `declareHiveTimeWake` → same routine | **FRESH** |
| Manual / user | `hive:wake` | `fireLaunchBlueprint('hive')` → same invoke route | **FRESH** |
| Inbox / await | `coord:send {wake:true}` to her owner id, or her own `events:await` | await pump → `wake-executor.ts executeWake` → `resumeCommandFor` | `--resume` (the one exception) |

### Where "fresh" is decided

`packages/operator-core/lib/endpoint-route/routes/harness/spawn.ts` (the
`/invoke?bpkind=hive` route): mints `nativeSessionId = randomUUID()` **fresh on
every fire** and passes it as `PAPERCUSP_NATIVE_SESSION_ID`. Then
`libs/papercusp/packages/orchestrator/src/invoke.ts` turns that into
`claude --session-id <uuid>` — which **creates a new session**, never `--resume`.
Because the uuid is freshly minted each fire, no transcript is ever continued.

The session id is *recorded* in `adv_sessions` so the **inbox/await** path
(wake-executor) *could* later `claude --resume <that id>` — but that path
resumes the LAST short fresh session (one turn), never a forever-transcript.

### The easy way to get it wrong

The misread conflates three true-but-unrelated facts: (a) the BEE forced
session id at `operator-spawn.ts:646-656` (that's `fleet:spawn`, recorded so a
bee *pane* can `--resume`); (b) the `spawn.ts` comment noting a bee's
`coord:send {wake:true}` resumes the Queen via wake-executor; (c)
`resumeCommandFor` building `claude --resume`. None of those is the Queen's
scheduled-wake path.

## Consequence

- The Queen ALREADY re-derives her working state from durable world-state every
  scheduled wake — and it works. Her load-bearing cross-wake state lives in
  durable artifacts (work-item claims, `blocked_by` edges, priorities, the
  `hive:declare-wake` routine, presence, the decision ledger), not the
  transcript.
- To make the Queen **uniformly** fresh (close the one `--resume` path), the
  cutover is in `wake-executor.ts executeWake`: detect a hive-operator session
  by its `adv_sessions` label (`hive · <slug>/<role>`,
  `hiveInstallSlugFromLabel()`) and route its ended-session wake through the
  SAME fresh hive launch (`fireLaunchBlueprint('hive')`, the wake text as
  kickoff) instead of `resumeCommandFor`. On fire-failure: PARK, never resume
  (the always-armed time/watchdog wake re-surveys). All other agents resume as
  before. (queen-brief-cache-assembly B-01 / P-012, channel `hive-fresh-wake`.)

## How to verify

`grep -n 'randomUUID\|--session-id' spawn.ts invoke.ts` shows the fresh mint +
`--session-id` create. `resumeCommandFor` (`--resume`) is reached only from
`executeWake`, which is the await/inbox pump — not the hive routine/blueprint
path. Don't trust a prose claim that "the Queen resumes" without tracing the
`fireLaunchBlueprint('hive') → invoke?bpkind=hive → --session-id` chain.
