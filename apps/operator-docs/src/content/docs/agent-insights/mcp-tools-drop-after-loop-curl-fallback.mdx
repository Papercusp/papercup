A looped agent (the owner routinely runs overnight `/loop` autonomous runs) can
**silently lose all papercusp-su MCP tools** after the `/loop` skill reloads the
tool environment. It cannot `coord:declare-intent`, claim work, consult peers, or
write memory — so it drops out of the fleet coordination everything relies on,
**while still appearing active**. Multiple agents hit this in one overnight run
(EI-1740) and recovered with the curl bridge below.

## Symptom — how to know your tools dropped

- A direct call to any `mcp__papercusp-su__*` tool returns **`No such tool available`**.
- `ToolSearch` (select: or keyword) **cannot find them** — they are not even in the
  deferred set.
- **Generic tools survive**: `Task*`, `Web*`, `Cron*`, `browser`, `LSP`, `Read`/`Bash`.
- It usually appears right after the `/loop` (or another skill) reload — you'll have
  seen a large deferred-tools system-reminder.

## Root cause

The Claude Code **harness rebuilds its tool registry on a skill reload** and drops
the HTTP MCP server's advertised tools. **This is a harness bug, not the papercup
repo** — the papercusp-su server is healthy and still serving. (Tracked: EI-1740;
the deeper ask is that MCP-server tool advertisements survive a `/loop` reload.)

## The fix you can apply right now — curl the HTTP MCP server directly

`papercusp-su` is a **stateless HTTP MCP server** (`.claude.json` →
`mcpServers['papercusp-su']`: `type: http`, an `?superuser=1` URL on
`http://localhost:3070/api/mcp`, a `Bearer` token). A plain `curl` POST of a
JSON-RPC `tools/call` works **without** an `initialize`/session handshake.

<Aside type="caution" title="Two required query params">
- **`workspace=papercusp-workspace`** is REQUIRED, or you get
  `scoped_superuser_workspace_unresolved`.
- **`client=<your established coord ownerId>`** is REQUIRED for identity-bearing
  tools (`coord:*`) — without it: `resolveAgentIdentity: superuser context is
  missing uiClientId`. Pass the ownerId your lane already uses (from `coord:whoami`
  before the drop, or your declared identity) so coordination stays continuous —
  the env `$PAPERCUSP_SID` may differ from your established identity.
</Aside>

### Verified one-shot (this exact call returned the correct identity)

```bash
TOKEN=$(node -e "const fs=require('fs');const p=JSON.parse(fs.readFileSync(process.env.HOME+'/.claude.json','utf8'));process.stdout.write((p.mcpServers['papercusp-su'].headers.Authorization||'').replace(/^Bearer /,''))")
OWNER=su-...your-established-ownerId...   # from coord:whoami
curl -sS -X POST "http://localhost:3070/api/mcp?superuser=1&workspace=papercusp-workspace&client=$OWNER" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"coord:whoami","arguments":{}}}' \
  | sed -n 's/^data: //p'
```

The response is an SSE stream; the answer is on the **`data:` line** —
`.result.content[0].text` holds the tool's JSON output.

### Reusable helper (drop into your shell for the rest of the loop)

```bash
psu() {
  # psu <tool> [json-args]  — call a papercusp-su MCP tool over the HTTP bridge.
  # Requires PSU_OWNER (your established coord ownerId); PSU_WS defaults to papercusp-workspace.
  local tool="$1" args="${2:-{}}"
  local owner="${PSU_OWNER:?set PSU_OWNER to your coord ownerId}" ws="${PSU_WS:-papercusp-workspace}"
  local token; token=$(node -e "const fs=require('fs');const p=JSON.parse(fs.readFileSync(process.env.HOME+'/.claude.json','utf8'));process.stdout.write((p.mcpServers['papercusp-su'].headers.Authorization||'').replace(/^Bearer /,''))")
  curl -sS -X POST "http://localhost:3070/api/mcp?superuser=1&workspace=$ws&client=$owner" \
    -H "Authorization: Bearer $token" -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"tools/call\",\"params\":{\"name\":\"$tool\",\"arguments\":$args}}" \
    | sed -n 's/^data: //p' \
    | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{try{const r=JSON.parse(s).result;console.log((r&&r.content&&r.content[0]&&r.content[0].text)??JSON.stringify(r))}catch(e){console.log(s)}})"
}
# examples — keep coordinating with your tools gone:
#   PSU_OWNER=su-xxxx; psu coord:whoami
#   psu coord:declare-intent '{"intent":"...continuing my lane via the curl bridge..."}'
#   psu 'coord:send' '{"to":["peer"],"summary":"..."}'
#   psu work_items:claim '{"id":"EI-1234"}'
```

Every papercusp-su tool is reachable this way (same names + args as the MCP tools).
Keep your `coord:declare-intent` / `coord:send` / claims flowing so you stay visible
to the fleet.

## The automated complement

An HTTP-bridge **auto-recovery** (re-route MCP calls through this endpoint when the
native tools drop) is being built separately (WI-260 / WI-258, su-42cb0) and is
confirmed working — several agents ran whole overnight loops through it. This page
is the **manual fallback + the underlying knowledge** for when the bridge isn't up,
or to understand what the bridge does.
