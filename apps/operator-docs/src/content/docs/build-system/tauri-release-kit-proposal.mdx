## The ask

Can the cross-platform (Linux / macOS / Windows) desktop build + release
pipeline be abstracted into a generalized shared library that **both papercusp
and myapp** use?

**Short answer: yes — the release *orchestration* generalizes cleanly; the
*sidecar build* does not and must stay a per-app injected seam.** That split is
the whole design.

## What the pipeline does today

The canonical tree is the **`papercup/papercusp-desktop/` git submodule**
(v0.0.2). It builds three platform families, all driven from `bin/`:

| Layer | Driver | Where it runs |
|---|---|---|
| Linux `.deb` / `.AppImage` / `.rpm` (x86_64, opt. arm64) | `bin/release-local.sh` → `tauri build` | dev host, locally |
| macOS universal `.dmg` | `bin/mac-vm-build.sh` → `tauri build --target universal-apple-darwin` | macOS VM over SSH (`:2222`) |
| Windows `.msi` + NSIS `.exe` | `bin/build-windows-on-vm.sh` → `win-build.ps1` | Windows VM over SSH (`:2223`); WSL2 runtime distro from `scripts/build-rootfs.sh` |

`bin/release-local.sh` is the spine. Its steps:

1. **Version bump** across `package.json`, `src-tauri/tauri.conf.json`,
   `src-tauri/Cargo.toml`.
2. **Build the sidecar** (`bin/build-desktop-sidecar.sh`, ~1,070 lines).
3. **`tauri build`** per target — Tauri does native bundling + minisign signing
   in one shot, keyed by `TAURI_SIGNING_PRIVATE_KEY_PATH`.
4. **Generate `latest.json`** (the auto-updater manifest) — maps
   `{platform → {url, signature}}` against the GitHub release download URL.
5. **Commit + tag + push** (`desktop-vX.Y.Z[-channel]`).
6. **`gh release create/upload`** (idempotent, `--prerelease` for alpha/beta).

## The core insight: two layers, only one generalizes

The pipeline is **release orchestration** wrapped around a **sidecar build**,
and they generalize very differently:

- **Release orchestration is domain-free.** Version bump, the `tauri build`
  target matrix, signing, `latest.json` generation, `gh release` upload, and the
  Mac/Windows **VM SSH orchestration** know nothing about what the app *is*.
  This is the shareable half.
- **The sidecar build is wildly app-specific.** Papercusp's
  `build-desktop-sidecar.sh` is **~1,070 lines** bundling the operator UI +
  harness + orchestrator + MCP server + node-pty + embedded-postgres + pgvector
  + external binaries (omp, gh, MinGit, node) + a WSL rootfs tarball. MyApp's
  `apps/desktop/scripts/build-sidecar.mjs` is **~42 lines** of esbuild over one
  `serve.ts`. There is nothing to share here — it must be an **injected step**.

So the library owns the *dance*; each app supplies a `buildSidecar()` plugin and
a config object.

### Generic vs injected boundary

| Concern | Generic (in the kit) | Injected per-app (seam) |
|---|---|---|
| Version bump | ✅ field-path-driven updater | which files/fields |
| `tauri build` matrix | ✅ Linux x64/arm64, Win cross, Mac universal | which targets enabled |
| Signing | ✅ already an env-var seam | key path / passphrase |
| `latest.json` / updater manifest | ✅ generator | GH download base URL |
| `gh release` create/upload | ✅ idempotent driver | owner/repo, tag pattern, channel→prerelease |
| Mac/Windows **VM orchestration** | ✅ SSH/SCP/rsync boilerplate | VM host/port/user/key, build dir |
| WSL rootfs builder | ✅ Docker bootstrap algorithm | pkg list, output path |
| **Sidecar build** | ❌ stays per-app | the whole `buildSidecar()` impl |
| App metadata | ❌ | name, id, bundle targets, category, publisher |

## Where it would live, and how it's consumed

MyApp already consumes the shared `@papercusp/*` libs (`@papercusp/sse`,
`@papercusp/sync`, `@papercusp/ui-primitives`, `@papercusp/embedded-pg-discovery`,
…) via workspace `*` deps — and **those `*` deps resolve to git submodules**:
myapp's `workspaces` maps `@papercusp/sync` → its local `libs/sync`, which is a
submodule of the shared `Papercusp/sync` repo (the same repo papercup vendors at
`libs/generic/sync`). So the kit should follow that **same shared-submodule
pattern**:

> **`@papercusp/tauri-release-kit`** — a standalone repo (like `Papercusp/sync`)
> vendored as a submodule by **both** papercup (`libs/generic/tauri-release-kit`)
> and myapp (`libs/tauri-release-kit`), exposing (a) a typed
> `TauriReleaseConfig` + programmatic API and (b) a thin `bin/` CLI. Each app adds
> a small `release.config.ts` + a `bin/release` wrapper.

> **Build it in-tree first, extract to a shared repo second.** Per CLAUDE.md a
> domain-free lib *starts* as `libs/generic/<name>` — which is exactly where it
> lives now (feature-complete, 56 tests green). Promoting it to a standalone repo
> + submodule (so myapp can vendor it) is the bridge step, and it's
> **owner-gated** (it creates a GitHub repo + rewrites two `.gitmodules`).

A git-submodule of the whole desktop tree was considered and rejected: myapp
deliberately does not submodule papercusp, and the desktop *shells* legitimately
differ (myapp builds its own SPA + a tiny sidecar; papercusp serves
operator-vite + the heavy sidecar). Sharing the **kit** (logic), not the
**shell** (the Tauri app), is the right grain.

### Seam contract (shipped — `libs/generic/tauri-release-kit/src/types.ts`)

The shipped `TauriReleaseConfig` (authoritative source: `types.ts`):

```ts
export interface TauriReleaseConfig {
  appName: string;              // "Papercusp"
  appId: string;                // "com.papercusp.desktop"
  root: string;                 // desktop app root (where src-tauri/ lives)
  repo: { owner: string; name: string };
  version: string;              // e.g. "0.2.1"
  channel: Channel;             // 'alpha' | 'beta' | 'stable'
  versionFiles: VersionFile[];  // [{path, kind: 'json'|'cargo-toml'}]
  targets: TargetKey[];         // flat array: ['linux-x86_64', 'macos-universal', …]
  signing: SigningConfig;       // { keyPath, passwordEnv? }
  buildSidecar: BuildSidecar;   // ← the injected seam: (ctx: SidecarContext) => Promise<void>
  latestJsonUrl: (a: { tag: string; name: string }) => string;
  tagFor?: (version: string, channel: Channel) => string;   // override default tag scheme
  classifyArtifact?: (path: string) => PlatformKey | null;  // override artifact→platform mapping
  vm?: Partial<Record<TargetKey, VmConfig>>;  // per-target SSH frame (Mac/Windows)
}
```

`buildSidecar` is the firewall: papercusp wires in its 1,070-line bash; myapp
wires in its esbuild. The kit never knows the difference.

## Migration order

1. **Canonicity (resolved — P-002).** Three desktop trees exist:
   - `papercup/papercusp-desktop/` — **submodule, v0.0.2, CANONICAL** (has the
     release + VM build scripts). The kit's papercusp adoption targets this.
   - `papercupai-workspace/papercusp-desktop/` — standalone, v0.0.1, **stale**;
     it lives *outside* the papercup repo, so it can't be retired from here —
     flagged for owner cleanup.
   - `papercup/libs/papercusp/apps/desktop/` — a v0.0.1 second app, but
     `branding.md` references it as a deliberate "secondary in-repo desktop app"
     (icon-pack mirror), so it is **not** auto-deleted — whether to retire it is
     an owner judgment call, not a safe autonomous removal.

   Net: canonical is recorded; no destructive deletes were made (both non-canonical
   trees are either out-of-repo or referenced).
2. **Extract the kit** behind the seam; **papercusp adopts it first** — its
   `bin/release-local.sh` becomes a thin wrapper over the kit. Prove byte-identical
   (or intentionally-improved) artifacts.
3. **MyApp adopts second** — add `release.config.ts` + `buildSidecar` (its
   esbuild) + a `bin/release`, giving myapp the Linux/Mac/Windows release flow
   it currently lacks entirely.

## MyApp adoption (ready once the kit is a shared submodule)

The kit is already proven app-agnostic — a second-app-shaped config runs through
`runRelease` unchanged (proven by the kit's app-shape test).
Once the kit is vendored into myapp as `libs/tauri-release-kit`, myapp adds
two files (and nothing in the kit changes):

```ts
// apps/desktop/bin/release.config.ts (myapp)
export function makeMyAppConfig({ version, channel }): TauriReleaseConfig {
  return {
    appName: 'MyApp',
    appId: 'com.myapp.desktop',
    root: DESKTOP_ROOT,
    repo: { owner: 'my-org', name: 'myapp' },
    version, channel,
    versionFiles: [
      { path: 'package.json', kind: 'json' },
      { path: 'src-tauri/tauri.conf.json', kind: 'json' },
      { path: 'src-tauri/Cargo.toml', kind: 'cargo-toml' },
    ],
    targets: ['linux-x86_64'],            // its tauri.conf ships deb+appimage
    signing: { keyPath: '~/.myapp/signing/myapp.key' },
    buildSidecar: async ({ root, ports }) => {       // the seam: ~42-line esbuild
      await ports.exec.run('npm', ['run', 'build:spa'], { cwd: root });
      await ports.exec.run('node', ['scripts/build-sidecar.mjs'], { cwd: root });
    },
    latestJsonUrl: ({ tag, name }) =>
      `https://github.com/my-org/myapp/releases/download/${tag}/${name}`,
  };
}
```

`apps/desktop/bin/release.ts` is the *same* thin CLI as papercusp's. Every
difference is config — appId, repo, bundle targets, and the sidecar seam (myapp's
esbuild vs papercusp's 1,070-line bash). This hands myapp the version-bump +
`latest.json` + gh-release + auto-updater flow it has **none** of today.

## Risks & timing

- ⚠ **The release scripts are being actively stabilized right now.** The
  `windows-public-release-readiness-2026-06-25` drive (and the Mac drive) are
  editing `build-windows-on-vm.sh`, Authenticode signing, and the WSL rootfs as
  of this writing. Refactoring mid-cut risks destabilizing a live public
  release. Safest sequencing: extract **after** that release lands, **or** scope
  a first pass to the **stable Linux x86_64 core only** (the part not in flux)
  and prove it on both apps before touching the VM paths.
- The sidecar seam must be drawn carefully — papercusp's bundling pulls ~1GB of
  external binaries with platform-specific exclusions (omp/code-server dropped on
  Windows for NSIS size limits); these stay entirely on papercusp's side of the
  seam.
