            <th>Term</th>
            <th>Definition</th>
            <th>Example</th>
          </tr>

        <tbody>
          <tr>
            <td><strong>Harness</strong></td>
            <td>A long-running iteration loop made of named roles invoked with fresh contexts that hand off via a structured state store.</td>
            <td>The role substrate in <code>libs/papercusp/packages/harness/</code>.</td>
          </tr>
          <tr>
            <td><strong>Hive</strong></td>
            <td>An operator over a fleet — a root install minted from a <code>kind:&apos;hive&apos;</code> blueprint. Its single judgment layer (the Queen) surveys the blackboard, decides with agency, creates/supervises harnesses, and declares its own next wake. Distinct from a <code>kind:&apos;harness&apos;</code> blueprint, which is a feature pipeline the Hive creates.</td>
            <td>A coding Hive from the <code>coding</code> blueprint, placing work onto Bees and spinning up <code>coding-factory</code> harnesses per feature.</td>
          </tr>
          <tr>
            <td><strong>Blueprint</strong></td>
            <td>The recipe that superseded <em>template</em> — a declared spine of roles, models, dispatch/triggers, and recommended plugins. <code>kind:&apos;hive&apos;</code> blueprints mint a Hive operator; <code>kind:&apos;harness&apos;</code> blueprints mint a feature pipeline.</td>
            <td><code>coding</code> (hive), <code>coding-factory</code> (default pipeline harness), <code>coding-solo</code> (single-worker baseline), <code>research</code>.</td>
          </tr>
          <tr>
            <td><strong>Bee</strong></td>
            <td>The generic operator-world worker the Queen places ranked work + a brief onto. Carries no pipeline spine and no chunk requirement (decoupled from the pipeline <code>worker</code> guards); the pipeline roles apply only when a Bee explicitly spins up a coding harness.</td>
            <td>The Queen places a work item onto a Bee, which does the task or spins up a <code>coding-factory</code> harness for it.</td>
          </tr>
          <tr>
            <td><strong>Queen</strong></td>
            <td>The Hive blueprint&apos;s placement-specialist decider — the operator role tuned toward placement: <code>fleet:spawn</code>/<code>drain</code> and work-list shaping. Same judgment layer as the operator, dial turned toward fleet management.</td>
            <td>The Queen decides which Bees run, drains idle ones, and shapes the ranked work list each wake.</td>
          </tr>
          <tr>
            <td><strong>Install</strong></td>
            <td>A specific configured harness — its goal, its plugins, its UI, its DB schema. An install is what users actually run.</td>
            <td>A coding Hive spun up from the <code>coding</code> blueprint. (The original Papercup 5-director autonomous-AI-company demo is retired — preserved-not-active in <code>_retired/papercup</code>; migration 192 dropped the org-simulation tables.)</td>
          </tr>
          <tr>
            <td><strong>Role</strong></td>
            <td>A named agent invocation — a <em>prompt file</em> + an entry in the orchestrator's decision table. Always with fresh context.</td>
            <td>The shipped pipeline roles are Scoper, Architect, Worker, Validator, Reviewer, Debugger, Documenter, Curator (the coding-factory pipeline runs scoper &rarr; architect &rarr; worker &rarr; validator &rarr; reviewer &rarr; documenter &rarr; curator). Orchestrator is a separate coordinator/decider role, not a pipeline stage — see <code>AGENT_ROLES</code> in <code>packages/agent-mcp/src/role-config.ts</code>. Plus user-defined roles via plugins.</td>
          </tr>
          <tr>
            <td><strong>Harness template</strong></td>
            <td>A reusable recipe for spinning up a harness. One template → many concrete harness <em>instances</em>; each instance has its own goal, project dir, state. Templates declare their roles, default models, and the plugins they recommend.</td>
            <td>The shipped coding blueprints: <code>coding</code> (the <code>kind:&apos;hive&apos;</code> Hive operator), <code>coding-factory</code> (the default per-feature pipeline harness), and <code>coding-solo</code> (the single-worker baseline). One user spins up one <em>instance</em> per project. (The retired <code>papercup-org</code> 5-department company is no longer a spinnable template.)</td>
          </tr>
          <tr>
            <td><strong>Plugin</strong></td>
            <td>A package that extends one or more harness instances with new capabilities — actions (buttons), routes, lifecycle hooks, DB schemas, custom UI tabs. Plugins are installed once globally and mounted into harness instances at runtime; their behaviour is gated by capability tiers (§10).</td>
            <td><code>@papercupai/cloudflare-pages</code> contributes a "Publish" button; <code>@papercupai/vscode-server</code> contributes a code-server tab; <code>@papercupai/slack-notifier</code> sends a Slack message on <code>mission-done</code>. Multiple plugins compose per instance.</td>
          </tr>
          <tr>
            <td><strong>Marketplace package <code>kind</code></strong></td>
            <td>The discriminator that tells the marketplace + Cupboard which install pipeline a published artifact follows. Implemented as a five-kind storefront (<code>LISTING_KINDS</code> in <code>packages/operator-core/lib/cupboard/types.ts</code>): <code>harness</code> (the repo&rarr;Hive lookup index), <code>blueprint</code> (a GitHub-repo-backed harness recipe — the term that superseded the original <code>template</code>), <code>plugin</code>, <code>tool-pack</code> (the runtime-less code-tool pack — renamed from <code>pack</code> by migration 008; the legacy <code>pack</code> value still parses as an alias), and <code>learning-pack</code> (a distributable set of curated hive learnings).</td>
            <td>All five go through the same publish + signing + retraction infrastructure; only the install handler differs. <code>blueprint</code> + <code>learning-pack</code> listings publish pending and surface only after operator approval.</td>
          </tr>
          <tr>
            <td><strong>Goal</strong></td>
            <td>The top-level mission. Every task traces back to a goal through a parent chain. Goals can themselves nest.</td>
            <td>"Build a habit-tracker mobile app and ship to TestFlight" or "Run an autonomous marketing agency."</td>
          </tr>
          <tr>
            <td><strong>Pending event</strong></td>
            <td>An entry in the queue the orchestrator reads on each tick. Sources: cron routines, webhooks, API triggers, completion deltas.</td>
            <td>Routine "weekly-briefing" fires at 9am Monday → inserts <code>&#123;&#123;role: narrator, due: 09:00&#125;&#125;</code>.</td>
          </tr>
        </tbody>
      </table>
