title: 6. Orchestrator + pending_events

<p>
        Papercusp uses a <strong>centralized orchestrator</strong> rather than per-agent heartbeats. Why:
      </p>

      <aside>
        <strong>Implemented (with evolution).</strong> The single all-deciding LLM "orchestrator" role of this
        design shipped as a <em>split</em>: the orchestrator is now the deterministic <em>code</em> selector
        (`packages/operator-core/lib/dbos/orchestrator-loop.ts`) that starts a durable per-feature pipeline, and the
        per-feature LLM decider keeps the distinct name <code>director</code> (the legacy
        `prompts/orchestrator.md` is archived under `_archived/`). External events still land in
        `harness_shared.pending_events` (NOTIFY/LISTEN via `pending-events-listener.ts`), but the scheduled-tick
        path is the DBOS <strong>routines engine</strong> (see §9): a cron routine now fires the
        `system:blueprint-run` action directly rather than enqueuing a `pending_events` row for the orchestrator to
        consume. The decision verbs below are real (`NEXT_WORKER`, `NEXT_VALIDATOR`, …); each blueprint declares its
        own vocabulary in `spine.edges`.
      </aside>

      <ul>
        <li><strong>No wasted wakeups</strong> — only the orchestrator polls. The other agents stay asleep until summoned.</li>
        <li><strong>Centralized auditing</strong> — every decision is one orchestrator output you can trace.</li>
        <li><strong>Cheap state visibility</strong> — orchestrator sees the whole picture in one prompt.</li>
        <li><strong>Drift control</strong> — sequential decisions, predictable order.</li>
      </ul>

      <p>
        External events (cron, webhook, API) write to a `pending_events` queue. The orchestrator consumes it on each tick, alongside its other inputs:
      </p>

      

```
     pending_events
     (queue)
        ▲
        │ inserts from:
        ├── cron-routine ticker (substrate)
        ├── webhook handlers
        ├── API triggers
        └── completion-delta hooks (e.g. task→passed → notify reviewer)
        │
        ▼
  ┌────────────────────────────────┐
  │   ORCHESTRATOR (1 per harness) │
  │                                 │
  │   reads:                        │
  │     - tasks (queue state)       │
  │     - pending_events            │
  │     - issues, worker_log        │
  │     - goal lineage              │
  │                                 │
  │   emits:                        │
  │     NEXT_WORKER | NEXT_VALIDATOR│
  │     | NEXT_NARRATOR | NEXT_<plugin>│
  │     | DONE | ESCALATE           │
  └─────────┬───────────────────────┘
            │
            ▼ (substrate dispatches the named role)
```



      <p>
        Tick triggering can be:
      </p>
      <ul>
        <li><strong>Timer-based</strong> — a routine fires every N seconds, inserting a <code>&#123;&#123;kind: 'routine', target_role: 'orchestrator'&#125;&#125;</code> event</li>
        <li><strong>Event-triggered</strong> — substrate notices a new `pending_events` row (NOTIFY/LISTEN) and wakes the orchestrator immediately</li>
      </ul>

      <p>
        For idle harnesses, this is strictly better than per-agent heartbeats: zero wakeups when there's nothing to do.
      </p>
