# Authoring autonomous experts

A "direct-writing expert" is an autonomous specialist agent that the scoper consults during `MODE=replan` and that writes its own features into `harness_features` (tagged with a non-`product` `kind`). The first concrete role is `infra-reviewer`. This page is the recipe for adding the next one.

The pattern is intentionally thin — almost everything an expert needs is already in the substrate.

## When to add an expert (vs a feature)

Add an expert when:

- The work is **cross-cutting** — affects features the scoper would otherwise produce in isolation. Infra, security audits, schema migrations, accessibility audits, docs scaffolding.
- The decision **happens at planning time**, not implementation time. (If it's "during the build, do X," that's a build-script change, not an expert.)
- You want the **scoper to reason about whether to consult**. If it's "always run on every accept," that belongs in `MODE=replan` directly.
- The output is **features** OR **spec bullets** (see "Output modes" below). Most cross-cutting roles want features; exploratory roles can use spec bullets that feed back into scoper's planning loop.

If those don't fit, you probably want a feature, a build-script change, a plugin, or a new scoper mode.

## What you need to ship

For each new role, exactly two artifacts:

1. **A prompt file** at `prompts/<role>.md` (the agent's system prompt).
2. **A sidecar manifest** at `prompts/<role>.role.json`:

   ```json
   {
     "id": "<role>",
     "whenUseful": "Consult when SPEC additions <do X, Y, Z>. Do NOT consult for <out-of-scope cases>.",
     "output": { "kind": "features", "featureKind": "<kind-tag>" },
     "alwaysFireOn": ["<plugin-event-name>"],
     "budgetCents": 50,
     "featureSize": "small"
   }
   ```

That's it. Substrate-side, the dispatcher, the role registry, the kind-aware features import, and the scoper's cross-cutting-experts discovery all handle the new role automatically. **No code changes, no scoper.md edits.**

Scoper discovers your role at runtime via `GET /api/harness/<slug>/expert-roles` and reads your `whenUseful` description to decide when to consult.

## Step 1 — write the prompt

Use `prompts/infra-reviewer.md` as the template. The required sections:

### Inputs the agent reads

The dispatcher sets these env vars; document them at the top of your prompt so the agent knows where to look:

| Env var | Source |
|---|---|
| `EXPERT_ID` | `ua-<n>`; matches `user_actions.id`. Stamp this on every feature you emit so the row traces back to your run. |
| `EXPERT_ROLE` | Your role's id (the `<role>` of `prompts/<role>.md`). |
| `EXPERT_REASON` | One-sentence summary of why you were dispatched (set by scoper). |
| `EXPERT_CONTEXT` | JSON blob with caller-supplied context — typically `{ linkedProposalId, newSpecBullets }`. Parse with `jq`. |
| `HARNESS_SLUG` | The harness's slug (set by run.sh's `harness_slug` helper). |
| `STATE_DIR` | `.harness/` in the project. |
| `PROJECT_DIR` | Project root. |

### Decision: should you emit features?

The agent's job is to read the SPEC change + any role-specific context (e.g. infra-contract for `infra-reviewer`) and decide whether the change requires features in your domain. Most consults should produce zero features — only emit when there's genuinely something to do.

### Emitting features

POST each feature directly to `/api/harness/$HARNESS_SLUG/features/import`. Always set `kind` to your role's tag (e.g. `'infra'`, `'security'`) and `metadata.expert_id` to `$EXPERT_ID`:

```bash
curl -sS -X POST "http://localhost:3055/api/harness/$HARNESS_SLUG/features/import" \
  -H "content-type: application/json" \
  -d "$(cat <<JSON
{
  "features": [
    {
      "id": "F-<KIND>-NNN",
      "title": "Concrete one-liner",
      "summary": "Self-contained description; worker agent shouldn't need to re-read the proposal",
      "status": "todo",
      "kind": "<your-kind>",
      "claims": ["<KIND>-NNN-assertion-id"],
      "metadata": {
        "expert_id": "$EXPERT_ID",
        "proposed_by": "expert:<your-role>",
        "proposal_id": "<from EXPERT_CONTEXT.linkedProposalId or null>"
      }
    }
  ]
}
JSON
)"
```

The `/features/import` endpoint enforces a cross-writer guard: if a feature with this id already exists with a non-`product` `kind`, it will only accept the update if the incoming `kind` matches the existing one. This means the scoper can't accidentally overwrite your features.

### Final stdout line

End with a single summary line so the substrate's telemetry can parse it:

```
::papercusp::<your-role>-done features=<N> reason="<EXPERT_REASON>"
```

## Step 2 — verify the role is registered

```bash
curl -sS http://localhost:3055/api/harness/<slug>/expert-roles | jq .
```

You should see your role's manifest in the `roles` array. If not, check:

- Both `prompts/<role>.md` AND `prompts/<role>.role.json` exist
- `id` in the sidecar matches the filename
- `output.kind` is `"features"` and `output.featureKind` is a slug-shaped string
- The sidecar JSON parses

## Step 3 — verify dispatch works

Dispatch your new role manually before relying on autonomous triggering. Use the bin/dispatch-expert helper:

```bash
bin/dispatch-expert <your-role> <slug> --reason "manual smoke" \
  --context '{"newSpecBullets":["- example bullet relevant to your role"]}'
```

Or POST directly:

```bash
curl -sS -X POST -H 'content-type: application/json' \
  -d '{"role":"<your-role>","reason":"manual smoke","context":{}}' \
  http://localhost:3055/api/harness/<slug>/experts/dispatch
```

You'll get back `{ ok: true, expertId: "ua-N", userActionId: N }`. Watch the run via:

- `tail -f $PROJECT_DIR/.harness/experts/runs/<role>-ua-N.log`
- The OperatorActionLog "Recent actions" panel in the harness dashboard
- `harness-features list <slug>` for the resulting features

## Lifecycle nuances

### Lockfile-based dedup

The dispatcher writes `.harness/experts/<role>.dispatch-lock` on entry and removes it on exit. Concurrent dispatches for the same role return HTTP 409 — by design. Scoper's prompt instructs it to NOT retry on 409 (the in-flight dispatch sees the same SPEC). The lock has a 5-minute TTL; orphaned locks (from dispatcher process crashes) get overwritten on the next legitimate dispatch.

### Dispatcher process owns the lifecycle

The dispatcher polls the agent's log file for the `__EXPERT_DONE__` sentinel and finalises the `user_actions` row when it appears. This means:

- If the dev server restarts during an expert run, the polling stops — the `user_actions` row stays at `running` until the next list query, then gets marked `failed` by the orphan-cleanup heuristic in `branch-actions.listRuns()` (yes, branch-actions; same heuristic applies).
- If the agent runs longer than the lock TTL, the dispatcher kills polling and marks the row failed. Tune `LOCK_TTL_MS` in `lib/expert-dispatcher.ts` if your role needs more time.

### Expert features survive scoper-replan

Scoper-replan's prompt explicitly preserves features where `kind` is anything other than `'product'` (or NULL — NULL is treated as legacy product). It can mark them deprecated but never deletes them. The `/features/import` endpoint enforces the same rule at the substrate level.

The next dispatch of the responsible expert is the only thing that should retire its own features.

## Substrate features now in place

These are all live and require no per-role configuration beyond the sidecar manifest:

- **Role registry** — sidecar `prompts/<role>.role.json` files are auto-discovered. Scoper sees the live list via `GET /api/harness/<slug>/expert-roles`.
- **`alwaysFireOn` triggers** — list plugin lifecycle / event names in the sidecar's `alwaysFireOn` array. The expert-triggers module dispatches the role automatically when those events fire from `firePluginLifecycle` / `firePluginEvent`.
- **Manual dispatch CLI** — `bin/dispatch-expert <role> <slug> [--reason ...] [--context ...]`.
- **Layer-3 smoke-build at promotion** — when a harness has `.harness/infra-contract.json`, `POST /:slug/promote/:id/confirm` runs the destination branch's build action after the merge; on failure, the merge is reverted and a `kind=infra` fix-the-build feature is created in the destination phase. Opt out via `.harness/config.json` `promotion.smokeBuild.enabled: false`.
- **Cross-writer guard at `/features/import`** — features with `kind != 'product'` cannot be overwritten except by an updater whose payload also carries the matching `kind`. Scoper-replan can't trample expert features even if it generates a colliding id.
- **Operator integration** — every dispatch records a `user_actions` row with `kind: 'expert.dispatch'`, `summary`, `detail_url` to the run log, and lifecycle (running → succeeded/failed). OperatorActionLog renders these alongside other long-running actions.

## Output modes

Both built-in and plugin-contributed roles support two output modes:

- **`output: { kind: 'features', featureKind: '<kind>' }`** — agent POSTs feature rows directly to `/features/import`. Worker agents pick them up alongside scoper's product features. Tagged with the given `featureKind` so scoper-replan's cross-writer guard preserves them. Most cross-cutting roles (infra, security, docs) use this.

- **`output: { kind: 'spec', specSection?: '<heading>' }`** — agent writes bullets to `$STATE_DIR/expert-spec-bullets/<expertId>.md`. On successful exit, the dispatcher appends those bullets to the project's `SPEC.md` under a marker comment. The next scoper-replan picks them up like user-authored bullets. Useful for exploratory roles (user-research, requirements-discovery) where features aren't yet the right output.

## Cost-cap enforcement

The role manifest's `budgetCents` is enforced two ways:

1. **Self-throttling**: `EXPERT_BUDGET_CENTS` env var passed to the agent's prompt; well-behaved agents stop early when approaching it.
2. **Hard kill**: the dispatcher polls the agent's stream-json log every 2s, sums `total_cost_usd`, and kills the entire process group via `SIGTERM` (escalating to `SIGKILL`) if cumulative cost exceeds `budgetCents × 1.15` (15% overshoot tolerance for the in-flight chunk that triggered the check). The user_actions summary records `KILLED — over budget at $X.XX (cap $Y.YY)`.

The 15% overshoot is intentional: `total_cost_usd` only updates at message boundaries, so a hard cap at exactly the budget would race the in-flight token batch.

## What this pattern lets you avoid

You don't need to:

- Write substrate code for a new role
- Migrate the schema
- Touch the scoper's runtime path (just its prompt)
- Manage agent spawn / log capture / telemetry yourself
- Coordinate with worker agents (they pick up your features the same way they pick up scoper's)

If you find yourself doing any of those, you're going off the rails — push back on the design before adding it.
