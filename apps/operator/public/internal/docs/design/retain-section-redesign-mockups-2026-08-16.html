Retain Section Redesign

Four treatments for rebuilding the “Also retained” sections as real cards — each visually separate from the page, each with its own scrollbar and infinite scroll — with “Shipped from ideas” removed, its statuses folded into the rows, and a new Work items from ideas section. Variant D (added after review) is the chosen direction: one pane for every type, lens weights separate.

2 & 3 · The redesign brief

All three mockups below implement the same three changes; they differ in layout and how far the information architecture goes.

CHANGE 1Sections become cards Raised surface, border, shadow — visually separate from the page background, not inlined onto it.
CHANGE 2Own scrollbar + infinite scroll Each card scrolls internally and pages more rows in as you reach the bottom (today: capped at 8 rows, no paging).
CHANGE 3Shipped section dissolved “Shipped from ideas” is removed; every row now carries its outcome chip, and a Shipped filter lives in each card header.
CHANGE 4Work items from ideas New section: ideas routed straight to work items (991 today). Plan-originated work items are excluded — they roll up under their plan in “Plans from ideas.”

Variant A

Stacked ledger cards

The closest evolution of what exists: the disclosure list becomes a vertical stack of full-width cards. Every section keeps its identity and full row width (long idea titles breathe); each card body is a capped-height scroll region with an infinite-scroll sentinel. Statuses live as chips on rows and as a filter in the header.

Variant D · owner’s pick

One retained ledger — every type, one pane

C taken to its conclusion: plans, work items, rubric changes, insight runbooks, and recipes are all tabs of one card — and the default All tab interleaves them newest-first, so “what has the loop banked lately?” is one glance and one scrollbar. Type glyphs carry identity, status chips carry outcomes, and plan rows still expand to show their plan-born work items. Lens weights stays separate: it is a distribution the loop steers by, not a feed, so it gets its own quiet strip below.

Per-type tab counts are the real corpus sizes (recipes: 13,561 auto-captured — which is exactly why the All feed interleaves by recent activity (last run / last update / routed-at), not raw corpus order, and why the per-type tabs matter). Filters apply where a type has statuses; runbook/recipe rows show their kind tag instead of a chip.

For
  • One scrollbar answers “what has the loop learned lately” across every store
  • Halves the visual weight of the view: two cards total, one of them slim
  • Same machinery everywhere: one unified feed with a kind filter — tabs are free after the first one
  • Lens weights, as the one non-feed, reads clearly as the loop’s steering wheel
Against
  • Cross-type interleaving needs a recency rule per type (last-run vs updated vs routed-at) — pick once, document it
  • 13.5k recipes would swamp a naive All feed — the recency interleave is load-bearing, not cosmetic
  • Section names (“Plans from ideas”…) become tab labels; the page loses its scannable section headers

Recommendation

Direction chosen (owner, 2026-08-16): Variant D — one unified pane for all five types, with Lens weights as the only separate section (a distribution, not a feed — it never belonged in a chronological ledger).

Earlier framing, for the record: A was the safe one-pass ship; C introduced the tabbed ledger and plan-born nesting that D generalizes; B is dropped. D ships on the C skeleton — same card, same scroll + keyset-pagination machinery; the tabs are a kind filter over one unified feed, so each additional type is nearly free.

Implementation notes (all variants share these)

  1. Data. “Work items from ideas” = scout_routed_ideas rows with routed_ref LIKE 'wi:%' (the improvement rail, 991 rows) joined to engineer_issues, excluding rows whose work item has source_plan_slug IS NOT NULL (plan-born). The same slug is what rolls items up under each plan in “Plans from ideas” (count(*) FILTER (state IN done/resolved)).
  2. Statuses. Keep the server-stamped verdict pattern from RetainShippedIdea.shipped (classified against ISSUE_SHIPPED_STATUSES server-side — the client re-typing state lists is the drift bug EI-18792873324746237 already fixed once). The Shipped header filter is a query arg, not a client filter, so it composes with paging.
  3. Infinite scroll. Replace SECTION_CAP = 8 with keyset pagination on the retain-extras resolver (cursor = (routed_at, idea_id), page ≈ 24); client keeps accumulated pages per section and an IntersectionObserver sentinel fires the next useSyncQuery page. SSE invalidation resets to page 1 (all sync via @papercusp/sync — no hand-rolled fetch loops).
  4. URL state. Active filter (and Variant C’s tab) go in nuqs (parseAsStringEnum), per the almost-all-state-in-nuqs rule — agents must be able to drive the view.
  5. Coordination. su-82a2b owns the active Blender plan and shipped the current “Plans from ideas” section (P-012) today; its P-009 “Learning tab design sync” item is still open — the implementation should land as an item on that plan (or linked to it) rather than a parallel lane.
