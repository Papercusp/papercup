Shared harnesses

Partially built — model is being implemented in phases

This page records the security model for shared harnesses (the peer-to-peer, multi-engineer sync substrate), the research it rests on, and the tradeoffs we are choosing intentionally. The model below is the agreed direction, tracked in the design memo apps/operator/docs/plans/papercusp-trust-model-2026-05-31.md. Sections marked Today describe the original (2026-05-31) insecure state; Recommended describes the target.

Build-state update (2026-06-13). The substrate trust layer is now substantially built: per-log admission (signed announce + GitHub-anchored verifyBinding attestation), revocation (revoked_pubkeys projection drop-list, gated on a live GitHub repo-admin check), and identity attestation (verifyAttestation) are all wired. Crucially, a confirmation audit (P-017, plan shared-hive-hardening-2026-06-13) verified that the model’s load-bearing invariant — every decision-bearing fact re-derives from GitHub at the point of action — holds across all current call sites. See The advisory-vs-trusted boundary for the verified call-site table. Per-op signing (Phase 2 below) remains a defense-in-depth future enhancement, not a shipped gate — the shipped model is per-log admission, so an admitted peer’s ops are trusted wholesale (the accepted equivocation tradeoff), which is why the GitHub re-derivation invariant is what actually carries the safety.

Build-state update (2026-06-25). Read admission is intentionally not a repo-collaborator permission gate. The pure decider in sync/hyperbee/read-admission.ts admits a log only after announce signature verification, GitHub-gist attestation verification, and the revoked_pubkeys veto. Boot adds two Hive-specific scope wideners: an already-known Hive member can be admitted from the local hive_members projection via trustedHiveMemberDeviceAdmission, and a same-Hive cross-member announce whose membership has not federated yet is buffered as pending and retried within the boot grace window. GitHub collaborator/admin permission remains the authority for repo binding, revocation actions, push/PR/merge, and shipped verification; it is not the swarm read-admission allow-list.

What a shared harness is

Section titled “What a shared harness is”

A shared harness lets several engineers collaborate on one coding project. Shared state — the feature queue, pull-request status, the contributor list, and feature “claims” — syncs peer-to-peer over the Holepunch stack and is projected into each peer’s local Postgres:

  • Hyperswarm — DHT peer discovery. The swarm topic = sha256("papercusp-substrate-v1:gh:<github_repository_id>"), derived from the public GitHub repo id, so it is discoverable, not a secret. gh:<repository_id> is only one of several topic bindings: the shipped multi-engineer (Hive) substrate is keyed by hive:<hive_pubkey>, which replaces the per-repo slug as the top-level federation unit (a Hive’s Swarms all join this one topic), with local:<workspace_id>/<slug> for pre-binding/private dev and an explicit topic:<hex> carrier so a link-joiner lands on the owner’s exact Hive topic rather than re-deriving a gh: topic that wouldn’t match.
  • Hypercore — one Ed25519-signed append-only log per device.
  • Autobase — merges many device Hypercores into one materialized view (concurrent, eventually-consistent).

Identity is anchored to GitHub: each device holds an Ed25519 keypair in the OS keychain. The OAuth GET /user channel is a local self-attestation only — it is never part of remote admission. Remote admission (post write-free-join) proves the device_pubkey ↔ github_user_id binding entirely from a device-signed announce plus verifyAttestation on a public GitHub gist — the gist pins owner.id === github_user_id, the body’s device_pubkey, and a device signature. There is no device-signed commit anywhere in the code: the old shared-repo contributor-file channel was removed in the write-free-join work.

The single most important fact: the authority for the one thing that truly matters — merging code — is GitHub itself. PRs merge through the GitHub REST API with a real user token, so GitHub’s write-access and branch-protection rules are enforced regardless of anything that happens on the swarm.

The trust problem

Section titled “The trust problem”

Original 2026-05-31 state: the substrate was wide open

Replicated Autobase ops were not signed, authenticated, or authorized on receipt — the only admission check was a schema-version filter. Because the swarm topic is derivable from the public repo id, any peer who could reach the DHT could join and write forged feature/PR/contributor/claim rows into every other peer’s local database. The designed defenses (an admission step gated on the two-channel binding, a revoked_pubkeys drop-list) existed on paper but had no production callers.

Update (2026-06-13): admission is now wired (Model B per-log: signed announce + GitHub-anchored verifyBinding + revoked_pubkeys veto — see packages/operator-core/lib/sync/hyperbee/read-admission.ts), so a peer is admitted only on a verified GitHub-anchored attestation, not by mere DHT reachability. What remains intentionally unbuilt is per-op signature verification at projection time: once a peer is admitted, its ops are projected wholesale (the accepted equivocation tradeoff). The forged-advisory-row surface is therefore narrowed to already-admitted peers and, per the verified invariant below, no decision-bearing action acts on those rows without re-deriving from GitHub.

Keep two threat models separate:

  • Untrustworthy local user — every local API route is auth: 'public' (127.0.0.1 only). It trusts whoever is on the desktop. Fine for a single-user desktop; not a shared-machine model.
  • Untrustworthy swarm peer (the serious one) — public topic + unsigned ops means a peer can poison every other peer’s local DB/UI. This is what the security layer exists to contain.

A code audit (2026-05-31) confirmed that GitHub is the only authorization actually enforced today. Everything Papercusp layers on top — the feature state machine, the PR “trusted authors” gate, the completion_ref “shipped ✓” verifier, contributor identity signatures, and substrate op-auth — is currently dead code, unwired, or self-asserted.

The decisive constraints

Section titled “The decisive constraints”
  1. Autobase will not authenticate ops for us — per-op signing and addWriter gating are our code, in the apply/projection seam.
  2. Signatures are necessary but not sufficient (Kleppmann) — a validly-admitted-then- malicious writer can sign false or equivocating rows. Full Byzantine resilience needs a hash-DAG causal layer we are not going to build.
  3. True removal / post-compromise security is impossible in an append-only multi-writer log — a revoked writer’s signed ops persist and replicate; “removal” means every honest peer drops them at projection time.
  4. A provenance signature proves authentication-at-a-time, not authorization or quality (Sigstore) — so the trustworthy “shipped” signal must come from GitHub’s merge state, not a self-reported receipt.
  5. GitHub already enforces the only hard authorization that matters. This is the escape hatch from the unsolved Byzantine-CRDT access-control problem.

Does Holepunch provide its own solution?

Section titled “Does Holepunch provide its own solution?”

Mostly the building blocks, not a turnkey access-control product:

  • Hypercore signs each log for free.
  • Autobase gives a writer set with addWriter/removeWriter, but you write the per-op check and the admission policy in apply.
  • blind-pairing-core (what Keet actually uses) is a real cryptographic invite/pairing handshake — admit-by-possession-of-invite-secret. This is Holepunch’s native admission answer.
  • Hyperswarm gives Noise-encrypted connections + a coarse firewall(remotePublicKey) reject hook.

What Holepunch deliberately leaves to the app: fine-grained capabilities (read/write/admin), identity binding (always app-layer — our GitHub anchor), and post-compromise security on removal (removeWriter stops new appends; it is not key-rotation/PCS). Of those, the only one we actually need is identity binding — which no library provides.

So the plan builds on Holepunch’s native primitives: per-op signature verification + GitHub-anchored addWriter (via blind-pairing, GitHub proof in userData) + a revoked_pubkeys projection drop-list.

Does Keyhive/BeeKEM fit our stack?

Section titled “Does Keyhive/BeeKEM fit our stack?”

Compatible in principle, but not native and arguably overkill:

  • It fits the ordering model — BeeKEM needs only a causal order, which Autobase provides. It’s the only post-compromise-secure option that works over a concurrent-merge log (MLS does not).
  • But it’s an Automerge-ecosystem Rust library (the beekem crate), not a Holepunch component. Adopting it means embedding that crate and running its control ops over Autobase — an unsupported combination, and it is pre-alpha, unaudited, BeeKEM not formally proven.
  • It couples authorization with encryption (it’s a continuous group key agreement). Our substrate data is plaintext to swarm members today; BeeKEM means encrypting group state with key rotation — a large shift that buys post-compromise security but is more than advisory data needs.
  • It still doesn’t solve identity — Keyhive defers human-identity binding to “a future layer above,” i.e. our GitHub anchor regardless.

Verdict on Keyhive

For the recommended model (advisory peer state re-derived from GitHub) we do not need Keyhive. Holepunch’s native primitives + the GitHub anchor are sufficient. Keyhive/BeeKEM is a deferred upgrade only if a concrete requirement emerges for state that must be confidential to members and survive a key compromise without GitHub.

Recommended model — GitHub is the authority of record

Section titled “Recommended model — GitHub is the authority of record”
  1. Authority of record = GitHub. Every decision-bearing fact (did it merge, who has write access, real PR status, who is a contributor) is re-derived from GitHub at the point of action — never trusted from a peer.
  2. Peer-synced rows = advisory cache (fast/offline UI), explicitly untrusted.
  3. Per-op Ed25519 signing + verify-on-receipt in the Autobase apply/projection path — defense-in-depth / UX integrity, not the authority of record. Sign sequence + freshness, not just content (Radicle’s 2026 replay-CVE lesson).
  4. GitHub-anchored log admission — signed announce + GitHub gist attestation verifies the device identity; revoked_pubkeys denies known-bad devices. Hive scope is then narrowed/widened by signed harness_slug, local hive_members, and pending retry for membership propagation. This is not a collaborator permission gate.
  5. Identity binding = a Keybase-style signed link — the GitHub-hosted device-signed proof is the cross-check that lets any peer detect a rewritten identity; revocation is a signed statement, not just a side list.
  6. Device-key rotation/recovery is GitHub-rooted — losing a device means re-running the two-channel binding from the new device; the old key goes on revoked_pubkeys. GitHub (the account) plays did:plc’s “higher-authority key” recovery role.
  7. “Shipped”/provenance = GitHub-derived — read merge state from GitHub; optionally record it as a signed in-toto-style attestation. Do not build a Rekor-style transparency log — GitHub already is the authority and stores attestations. (This also means the completion_ref “shipped” signal should be GitHub-derived, not a self-reported peer receipt.)
  8. Sybil/admission = verified GitHub identity plus Hive membership/revocation. The swarm topic is public, so unauthenticated devices are filtered by signed announce + gist attestation; shared-Hive cross-member scope is filtered by hive_members; and revoked_pubkeys is the hard local blocklist. The GitHub collaborator graph is still consulted at decision points that need repo authority, but it is not the read-admission allow-list.
  9. Do not adopt MLS or build a Byzantine-CRDT ACL.

Revocation chokepoints (built)

Section titled “Revocation chokepoints (built)”

Two revocation mechanisms are wired beyond the revoked_pubkeys admission drop-list:

  • PR auto-approve and auto-merge refuse a revoked contributor’s PR up front. A PR whose author is a revoked Hive contributor is denied (action skipped_revoked) before the trust / checks / approval gates — the strongest deny, overriding the trust list (it holds even for an author otherwise in trusted_authors). The live chokepoint resolves it via isHiveContributorRevoked and passes it into both tryAutoApprove and tryAutoMerge.
  • Owner-revocation of another contributor (revokeContributorViaGithub) is gated on a live GitHub repo-admin check (repos.get → permissions.admin) — the harness-owner authority. It works by unioning the target’s device pubkeys into the owner’s own contributor-row revoked_pubkeys and publishing it (the old “delete the user/<id> branch” lever became a no-op under write-free join, and an admin cannot delete another user’s attestation gist). Because load-revoked-pubkeys unions revoked_pubkeys across all contributor rows for the harness, that block federates via the owner’s log and is honored by every peer’s admission union.

Accepted-insecurity tradeoffs

Section titled “Accepted-insecurity tradeoffs”

Under this model we deliberately accept:

  1. Public, discoverable topic — swarm spam/DoS is mitigated (firewall + admission), not prevented.
  2. Advisory rows can be injected by an admitted identity — read admission proves identity and Hive membership, not truth. An admitted-then-malicious writer can still inject signed-but-false advisory rows (equivocation). Mitigation: nothing decision-bearing acts on it without GitHub re-derivation.
  3. No true removal / no post-compromise security in the append-only log — revocation is best-effort projection filtering; the data persists and replicates.
  4. Sybil resistance is mostly delegated to GitHub identity plus Hive membership — identity = GitHub account, bounded by the gist attestation and GitHub’s account-creation friction; cross-member shared-Hive writes also require a current hive_members device row or they remain pending/dropped.
  5. Per-op signatures don’t defeat a signed equivocator (Kleppmann) — accepted because state is advisory and GitHub-re-derived; we explicitly do not build a BFT-CRDT ACL.
  6. Identity binding inherits GitHub account integrity — a compromised GitHub account is a compromised identity (the same trust root as the merge authority, so not a new exposure).
  7. Local API stays loopback-trusted — a single-user-desktop model, not a shared machine.

Phased implementation

Section titled “Phased implementation”
  • Phase 1 — make peer state advisory + re-derive from GitHub. Highest value, lowest risk; neutralizes the forgery surface for anything that matters. Resolves completion_ref as a GitHub-derived “shipped” signal.
  • Phase 2 — per-op Ed25519 signing + verify-on-receipt in the apply/projection path (sign seq + content); drop unverifiable ops at projection.
  • Phase 3 — GitHub-anchored addWriter admission (two-channel proof in blind-pairing userData) + revoked_pubkeys projection drop-list; model the binding as a signed link.
  • Phase 4 — only if a threat model demands real PCS — Keyhive/BeeKEM membership.
