# DBOS system completion — fill non-cut capability gaps, wire-or-cut the dead roles, true up prompts to code

## Now

**State:** Draft — the synthesis of a full code-grounded audit of the legacy harness system (design soundness + prompt↔code fidelity, 2026-06-01) against the live DBOS engine. This **supersedes and absorbs** `dbos-pipeline-prompt-reconciliation-2026-06-01` (its orchestrator.md / pre-loop / CONVERT_ISSUES items are folded in as D-001/Phase 2/3). The audit found the DBOS migration is sound in its core (per-feature durable pipeline + chunk-loop worker are real improvements over the legacy global LLM-per-iteration loop), but it is **incomplete** in three ways this plan closes:
1. **Engine-parity gaps** — legacy capabilities NOT on the intentional cut list that DBOS silently dropped (pre-loop, CONVERT_ISSUES, debugger-before-worker).

3. **Prompt↔code drift** — ~10 places where a live role's prompt misdescribes the actual contract (monitor has no prompt file, documenter's DONE call no-ops, reviewer's stdout-vs-file gate, scoper's dead modes, etc.).

**Governing directive (avi, 2026-06-01):** PRESERVE every legacy capability EXCEPT the ones the retire plan (`dbos-retire-legacy-orchestrator-2026-05-31`) explicitly records as intentional cuts. ## Background — the audit verdict (FACTS, code-cited)

**Live engine:** DBOS durable per-feature pipeline (`apps/operator/lib/dbos/orchestrator-workflow.ts`, default-on since retire-plan P-009). Dispatcher (`orchestrator-dispatcher.ts`, 30s tick + on-settle refill) selects features in pure code (`selectFeaturesToDispatch`); per-feature decisions are made by the **`director`** role (`director.md`, 47 lines — accurate). The legacy `main-loop.ts` is RETIRED (revert via `PAPERCUSP_DBOS_ORCHESTRATOR=0`). Worker runs the chunk-loop via `run-worker-chunk-loop.ts` (shared by both paths since 2026-05-31).

**Runtime-foundation prerequisite (D-008 below — added from review):** this audit was *static / prompt-centric*. A runtime review caught two pre-existing bugs that, before their fix (retire-plan D-014, commit `e3e688df1`), made the DBOS worker step **throw before reading a single feature** — so none of this plan's behavior could have run: (1) `readFeaturesPg` queried a `source_plan_slug` column that exists only on the consolidated table, not per-schema `harness_features` (verified fixed: `state-pg.ts:84-92` now reads `metadata->>'source_plan'`); (2) `readPlan` crashed on legacy double-encoded `files` with `paths.map is not a function` (verified fixed: `chunk-plan-pg.ts:138` `normalizeStoredFiles`). These fixes are the foundation that makes the worker path execute at all — this plan **depends on D-014**, it does not re-do it. The deeper lesson (D-008): a static audit structurally cannot see "the path throws"; runtime verification must be an *early* gate, not Phase 4.

**Design verdict (JUDGMENT):** DBOS is a genuine improvement, not a lateral move — it pushed deterministic cross-feature *selection* into code and reserved the LLM for the one ambiguous call (per-feature next-step), gaining crash-recovery + failure-isolation the legacy loop lacked. The legacy global loop's LLM-per-iteration (incl. no-op `IDLE`/`CONVERTED`/`FEATURE_FREEZE` verbs) was its weakest axis. So: complete the DBOS system; do not resurrect the legacy loop's structure.

**The cut list (intentional, from retire-plan D-001/D-009/D-012, recorded here as D-REF):** `NEXT_HARNESS`, `NEXT_WORKER_CEO_MODE`, parallel `NEXT_WORKER N=k` lanes; competition / adaptive-tiers / synthesizer (flag-gated behind FLAGS.TESTING, not deleted, per retire-D-011). Everything below is NOT on that list.

## Phase 5 — Concurrency safety + promote-time parallelism (D-009/D-010/D-011)

The legacy orchestrator-LLM could *choose* not to co-dispatch two conflicting features; under the deterministic dispatcher that judgment vanished and **nothing replaced it** — concurrent features sharing a file currently race (verified: the chunk-loop `FileLockQueue` is in-process per subprocess, so two feature workers are invisible to each other's locks). Two complementary layers fix this: a **runtime lock floor** that guarantees safety regardless of any agent's judgment (D-010), and a **promote-time parallelism declaration** that lets the promoting agent express intended parallel/serial shape so conflicts are mostly avoided before they reach the floor (D-009). `blocked_by` enforcement + `order`-at-dispatch (D-011) make the agent's declared ordering actually mechanical, not advisory.

- **P-040** `todo` **(conflict-safety FLOOR — correctness-critical; the load-bearing item)** Route the worker chunk-loop through the existing `FileClaimCoordinator` seam (`@papercusp/file-claim`) to the **PG-backed lock backend the `locks:*` SU tools already use** (`apps/operator/lib/agent-tools/locks/{acquire,release,heartbeat}.ts`), instead of the in-process `FileLockQueue`. Concretely: change `worker-chunk-loop.ts:88` + `run-worker-chunk-loop.ts:159` + `invoke-once.ts:134` to type/accept the abstract `FileClaimCoordinator` (the seam already exists and has a conformance suite) rather than the concrete `FileLockQueue`; inject the PG-backed coordinator when running under DBOS with cross-feature concurrency, keep `FileLockQueue` as the default for the single-feature / test path. Result: two concurrent feature workers that touch the same file **serialize cross-process** on a TTL'd PG claim instead of racing. NB this is the SAME PG primitive the fleet-rate-limit brief (`BRIEF-fleet-rate-limiting-2026-06-01.md`) wants for its global spawn-semaphore — coordinate so there's one PG claim/semaphore layer, not two. Unit-tested (the file-claim conformance suite already covers cross-process visibility for the PG backend). blocked-by: P-006
- **P-041** `todo` **(promote-time parallelism — the optimizer)** Let the **promoting agent emit the wave/parallelism structure at promote time** (not pre-baked in the plan YAML before finalization). Extend `plans:promote` so the call can declare grouping — "these features run in parallel as wave N; these wait for wave N to drain" — promoting the current explicit-mode escape hatch to first-class. **Write the emitted structure back into the plan doc** (extend the `## Promoted` write-back so the realized wave/parallelism shape is durable, reviewable, and a re-promote is reproducible — consistent with plans-central). The promoting agent is the right decider here: at promote time the features are concrete, so it can judge intended parallel/serial shape better than the plan author could ahead of finalization. This is INTENT (avoid foreseeable conflicts); P-040 is the GUARANTEE (catch the unforeseen). Unit-tested. blocked-by: P-016
- **P-042** `todo` **(enforce the declared ordering)** Make per-feature `blocked_by` + `order` MECHANICAL, not advisory (today `promote.ts:427-428` writes them to `metadata` and the dispatcher reads neither). In the renamed orchestrator's selection: (a) `ORDER BY (metadata->>'order')::int ASC NULLS LAST, feature_id` in `readFeaturesPg` so the promoting agent's within-wave priority is honored (back-compat: un-ordered features fall back to feature-id, today's behavior); (b) defer a feature whose `metadata.blocked_by` peers aren't terminal (`passed`/`deprecated`) rather than dispatching it. This gives intra-wave ordering without forcing every dependency into its own serial wave (which over-serializes). blocked-by: P-016, P-041

### D-009 — Concurrent-conflict prevention: who decides, post-orchestrator-LLM (DECIDED by avi, 2026-06-01)
Date: 2026-06-01. The legacy orchestrator-LLM could choose not to co-dispatch two features it judged conflicting; the deterministic dispatcher dropped that judgment and nothing replaced it (verified: concurrent feature workers race — the chunk-loop `FileLockQueue` is in-process per subprocess, invisible across workers; `git`'s own index.lock only prevents corrupt commits, not logical clobbering). The fix is TWO complementary layers, NOT one — conflating them is the trap: **(1) a runtime lock floor (D-010) = the GUARANTEE** (catches conflicts no agent foresaw — a worker touching a shared util the author never anticipated); **(2) promote-time parallelism declaration (below) = the OPTIMIZER** (the promoting agent declares intended parallel/serial shape so foreseeable conflicts never reach the floor). avi's decision: **let the promote step EMIT the wave/parallelism structure (P-041), at promote time, written back to the plan doc** — rather than pre-baking it in the plan YAML before finalization. Rationale: parallelizability is better judged at promote time (features are concrete) than at authoring time (you're thinking about *what to build*, not *which files collide*); and writing it back keeps the plan the durable, reviewable, reproducible record (plans-central). Waves = coarse phases; `blocked_by` = fine intra-wave order (D-011); the lock floor = the net under both.

### D-010 — Conflict-safety FLOOR: route the worker chunk-loop to the EXISTING PG lock backend (DECIDED by avi, 2026-06-01)
Date: 2026-06-01. avi: "make the harness file lock queue use the same PG one already used by SU agents." Confirmed in code: there are TWO lock layers and only one is PG-backed. The `locks:*` MCP tools (`apps/operator/lib/agent-tools/locks/*`) ARE cross-process Postgres-backed (this is what stops SU agents/paperclip colliding). The orchestrator chunk-loop is NOT — `invoke-once.ts:134` does `new FileLockQueue()` per subprocess (in-process `Map`, `file-lock-queue.ts:28-30` says so). The `@papercusp/file-claim` `FileClaimCoordinator` interface is the **seam already designed to unify both backends** (docstring names "PG = uuid lock_id, in-process = …"; conformance suite carves out "cross-process visibility (only the PG backend has it)") — it was just half-wired: the orchestrator imports the concrete class, not the interface. So the fix (P-040) is small: flip `worker-chunk-loop.ts:88` / `run-worker-chunk-loop.ts:159` / `invoke-once.ts:134` from the concrete `FileLockQueue` to the abstract `FileClaimCoordinator`, and inject the PG-backed coordinator under DBOS concurrency. This is the SAME PG claim primitive the fleet-rate-limit brief wants for its spawn-semaphore — build one layer, not two.
