# Route audit — Phase 4 opening deliverable

**Date:** 2026-05-20
**Phase:** 4 of host-architecture v2 (Route migration after mandatory pre-flight audit).
**Status:** Audit framework + baseline snapshot. Per-batch migrations land as follow-up PRs that update the rows in this doc.

---

## Why this doc

The audit IS the first deliverable. Phase 4 of host-architecture v2 has 240 `route.ts` files under `apps/operator/app/api/**` and a four-axis classification rule. Migrating before the audit runs would mean re-migrating the wrong routes when their A1-ness surfaces during the work. The audit comes first, the migrations come second.

Every PR that migrates a route updates this doc's row for that route — `hint` becomes `decision`, the link points at the migration commit. New routes get added during creation. Closing the audit means every row has a decision.

## The four axes

From host-architecture v2 §6.1, applied per route:

| Axis | Question | What "yes" means |
|---|---|---|
| **a** | Does the handler hold non-transport state? | A1 |
| **b** | Is there pre/post handler work that doesn't belong in a transport-agnostic tool? | A1 |
| **c** | Does it touch cookies / cost-caps / feature-locks? | A1 |
| **d** | Is its wire contract stable? | Migrate only if all of a-c are "no" AND d is "yes" |

Any single "yes" on (a)-(c) → **A1-class.** Keep the route as a Hono / Next shim. The agent-chats precedent (`_hono/agent-chats.ts`, 419 LoC — transcript persistence + cost caps + feature locks + three rejected relocations) is the canonical A1.

Otherwise → **migrate** if the wire contract is stable; **review** if d is in question.

A fourth bucket is **consolidate** — loopback-gated routes that are simple enough to migrate but the migration target is the Principal RFC's `requirePrincipal()` sweep, not `defineTool`. These land in Phase 3b's implementation, not Phase 4 per se. Listed here for completeness.

## Buckets in this doc

| Bucket | Meaning | Next action |
|---|---|---|
| **substrate** | Already uses `defineTool` / endpoint-system dispatch. No migration needed; just verify telemetry plumb. | Confirm `transport: 'ipc' / 'http'` rows in `tool_invocations`; move on. |
| **migrate** | Audit-recommended migration to `defineTool`. | Per-PR migration; update row to `decision: migrated → <commit-sha>`. |
| **consolidate** | Loopback-only auth gate; small handler. Migrate auth to `requirePrincipal()` (Phase 3b), keep wire shape. | Phase 3b implementation. |
| **consolidated-already** | Already calls `requirePrincipal()`. Phase 3b sweep applied; closed. | None — done. |
| **A1** | A1-class. Stay as a Hono shim; do NOT migrate. | Update row to `decision: A1-exempt`; capture *which* axis triggered the exemption. |
| **review** | Script couldn't decide. Manual classification required. | Read the file, evaluate the four axes, write a row decision. |

## Baseline snapshot (2026-05-20)

Generated by `apps/operator/scripts/route-audit.mjs`. Run it any time to refresh:

```bash
node apps/operator/scripts/route-audit.mjs
node apps/operator/scripts/route-audit.mjs --family admin    # per-family detail
node apps/operator/scripts/route-audit.mjs --json > snap.json
```

Heuristics the script uses (per route):

- **substrate**: imports `@papercusp/agent-mcp` / calls `defineTool` / calls `dispatchProjectedTool`
- **nextH**: imports `next/headers`
- **cook**: reads `cookies()` or `req.cookies.*`
- **loop**: calls `isLoopback(...)` / `isLoopbackRequest` / `isLoopbackIp`
- **cost**: references `recordSpend` / `enforceCostCap` / `checkBudget`
- **lock**: references `featureLock` / `requireCapability` / `acquireFeatureLock`
- **pers**: calls `getOrgPg` / `getHarnessPg` / `getWorkspacePg` / `drizzle` / raw SQL DML
- **plug**: calls `getPluginHost` / `loadPlugin` / `pluginRuntime`
- **strm**: returns SSE (`text/event-stream`) or a `ReadableStream`

Hint resolution:
- any of `cost` / `lock` / `plug` → `A1`
- `cook` and not `substrate` → `A1`
- `loc > 200 && pers` → `A1` (size + persistence ≈ the agent-chats shape)
- `substrate` (already migrated) → `substrate`
- `loop && loc < 100 && !pers` → `consolidate`
- `pers && loc < 100 && !strm` → `migrate`
- `strm && !cost && !lock` → `migrate`
- otherwise → `review`

### What this tells us

- **174 / 240 → review.** The script can't decide ~72% of routes. That's the unavoidable manual-audit population; it's why the plan estimate is "ongoing through the calendar year, paced by audit output" rather than "8-12 weeks."
- **16 → A1.** All five `auth/*` routes are A1 by construction (cookies). The rest split across `plugins/` (plugin-host coupled) and a few one-offs. Confirming these as A1 takes minutes per route.
- **13 → substrate.** Already migrated. Verify telemetry on next sweep; close.
- **25 → migrate.** The high-confidence migration pipeline. Mechanical-ish; ~2-4 routes per PR.
- **12 → consolidate.** Will be cleaned up by the Principal RFC sweep (Phase 3b → §3 of `principal-rfc-2026-05-20.md`), not by Phase 4 directly.

The cheap wins are **substrate** (verify + close) and **A1** (confirm + close). Those land first as quick batches. Then the `migrate` bucket. The `review` bucket is the long tail.

## Worked example — auth/login

`apps/operator/app/api/auth/login/route.ts` (113 LoC):

| Axis | Answer | Why |
|---|---|---|
| a — non-transport state | yes | reads `users` from PG, sets a session cookie, audits the login |
| b — pre/post non-transport work | yes | rate-limit check, password hash compare, audit-log append |
| c — cookies / cost-caps / locks | yes | sets `papercusp_session` cookie |
| d — wire contract stable | yes | `/api/auth/login` is part of the public auth surface |

**Decision: A1-exempt.** Three yeses on a-c; the route is transport-coupled by definition. Stays as a Hono shim. No migration.

Same shape applies to all five `auth/*` routes — the script hinted A1 for all of them and the manual check confirms.

## Worked example — ui/intents/[id]/result (a false-positive caught)

`apps/operator/app/api/ui/intents/[id]/result/route.ts` (68 LoC). The script hinted `migrate`. The four axes alone *look* migratable:

| Axis | Answer | Why |
|---|---|---|
| a — non-transport state | no | reads one row by id, returns it |
| b — pre/post non-transport work | no | only loopback-gate + PG read |
| c — cookies / cost-caps / locks | no | none |
| d — wire contract stable | yes | tiny + stable JSON shape |

But the **caller-check** — the axis the four-axis test misses — flips it: the route is called only by browser components (`intent-dispatcher.tsx`), and it's the browser half of the `ui:dispatch` agent tool's contract. Migrating it to a `defineTool` would put a browser-callback endpoint in the agent tool catalog. **Decision: A1-exempt.** See the batch-2 correction below — this worked example is why the audit added the caller-check as a mandatory fifth question.

### migrate (0 — bucket fully audited, collapsed to A1)

The script hinted 25 routes `migrate`. **A full caller-check of all 25 found zero genuine migrations** — every one is plumbing, UI-data, admin, orchestrator-IPC, or transport. The batch-by-batch record is below; the bottom-line reframing is in "The `migrate` bucket is empty" further down.

**Batch 2 correction — `ui/*` (3 routes) reclassified `migrate` → A1-exempt.** The script hinted `migrate` (small + PG-touching + no streaming for two of them). Reading the routes contradicted the hint:

| route | script hint | decision | why |
|---|---|---|---|
| `app/api/ui/presence/route.ts` | migrate | **A1-exempt** | Browser→operator presence beacon. Called only by `UiPresenceProvider.tsx` / `use-ui-presence.ts`. The route IS the browser↔operator contract; migrating it to a `defineTool` would put a browser-telemetry beacon into the agent tool catalog (a category error). |
| `app/api/ui/intents/[id]/result/route.ts` | migrate | **A1-exempt** | Browser→operator intent-result callback. Paired with the existing `ui:dispatch` agent tool's long-poll. Same contract-surface argument. |
| `app/api/ui/intents/stream/route.ts` | migrate | **A1-exempt** | SSE long-poll (maxDuration 86400s) feeding the browser's intent dispatcher. Streaming browser-facing transport, not an agent-callable function. |

The `ui:*` *agent* surface already exists as proper `defineTool`s — `lib/agent-tools/ui/{list_clients,dispatch,get_state}.ts`. The three `/api/ui/*` routes are the browser half of that pair and stay as Hono/Next shims. This is the audit framework working as intended: the heuristic flagged 3 false positives, the human read corrected them.

**Batch 3 correction — `internal/*` (8 routes) reclassified `migrate` → A1-exempt.** All eight `/api/internal/*` routes are the **orchestrator→operator event bus**, not agent tools:

| route | caller | role |
|---|---|---|
| `internal/log-event` | `bash run.sh` `log()` | publishes log lines to the `<slug>:log/raw` bus |
| `internal/run-chunk` | orchestrator `invoke.ts` | fans subprocess stdout to the agent SSE bus |
| `internal/archive-event` | orchestrator | lifecycle event post |
| `internal/checkpoint-event` | orchestrator | lifecycle event post |
| `internal/feature-debug-note-event` | orchestrator | lifecycle event post |
| `internal/plan-review-event` | orchestrator | lifecycle event post |
| `internal/pr-event` | orchestrator | lifecycle event post |
| `internal/smoke-test-event` | orchestrator | lifecycle event post |

They authenticate with a **harness bearer** (validated against `harness_shared.token_index`) and the caller is `bash run.sh` / the TS orchestrator's `bus-posts.ts` — machine-to-machine, not an MCP client. Turning them into `defineTool`s would put orchestrator plumbing into the agent tool catalog. **All 8 A1-exempt** — they stay as Hono/Next shims; their wire contract is the orchestrator↔operator IPC boundary.

### Heuristic finding — the `migrate` bucket over-predicts

Two batches in, **11 of the original 25 `migrate`-hinted routes turned out to be A1** (3 `ui/*` + 8 `internal/*`). The script's heuristic — "small + PG-touching + no streaming" — describes *plumbing/contract routes* exactly as well as it describes *migratable agent functions*. It cannot tell the difference between "a typed function an agent should call" and "a typed POST the browser or orchestrator makes."

### The `migrate` bucket is empty — Phase 4 reframed

**All 25 routes the heuristic hinted `migrate` turned out A1.** Not one was a typed agent function hiding as a route. The operator's `app/api/**` surface is — definitively, by full audit of the heuristic's highest-confidence bucket — composed of:

- **substrate** — routes already dispatching through the endpoint system. These *are* the agent-tool surface.
- **A1 / plumbing** — UI-data routes, orchestrator IPC, admin ops, plugin-host bridges, sync transports, cookie auth. These are correctly route shims and always will be.
- **consolidate** — loopback-auth routes (all 12 swept onto `requirePrincipal`).

**There is no large "migratable route" population.** The host-architecture v2 plan's Phase 4 estimate ("ongoing through the calendar year") assumed one. The audit disproves it: the endpoint-system migration surface was already essentially complete — the ~23 substrate routes are the whole agent-tool catalog, and the right move for every other route is *leave it as a shim*.

**What this means for the plan:**
- Phase 4 is **not** a multi-month migration marathon. It's a **classification sweep** — read each `review`-bucket route, confirm A1-vs-substrate, record it. No code changes for the overwhelming majority.
- Phase 6b (layering enforcement, gated on "Phase 4 ≥75%") is reachable far sooner than projected — "75% migrated" was the wrong gate; "75% classified" is the real one, and classification is fast.
- The `review` bucket (~160 routes) will almost certainly resolve the same way: a few substrate, the rest A1 plumbing. Worth completing the sweep to be certain, but the *shape* of the answer is now known.

### review (~160 — classification sweep, not migration)

The remaining routes need a human read — but the expectation is set: classify A1-vs-substrate, record the row, move on. Migrations, if any, will be the rare exception, not the rule. Each batch claims a family, reads each route's caller, applies the four axes, lands a doc-only PR (or a code PR in the rare genuine-migration case).

### consolidate (0 remaining; 12 closed)

All 12 loopback-only-gated routes the Principal RFC implementation targeted are now migrated. Shipped 2026-05-20 across three batches:

- 7 `desktop/*` state probes — `requirePrincipal(req.headers)` (any auth, including loopback)
- 3 `admin/*` operations — `requirePrincipal(req.headers, { trust: ['trusted'] })` (preserves bearer-required gate)
- 2 `agent-mcp/*` console internal — `requirePrincipal(req.headers)` (any auth; el-admin-creds tightening deferred)

All 12 classify as `consolidated-already` per the updated audit script.

Phase 3b §4 walks the consolidation strategy. The consolidate bucket is now closed.

## PR cadence

- One PR per family or per ≤ 8 routes (whichever is smaller).
- Each PR updates this doc's row(s) **before** the migration commit so the audit state and the code state ship together.
- A PR may classify a row without migrating it (e.g. confirm A1-exempt). Classification is a real deliverable.

## Coordination with parallel work

- The 12-route `consolidate` bucket waits on Phase 3b's RFC sign-off (`principal-rfc-2026-05-20.md` §6 questions need answers). Don't touch these in Phase 4 PRs.
- Phase 6b layering enforcement (`apps/operator/layers/`) starts firing once routes start moving into `tsconfig.routes.json`'s include glob. Phase 4 migrations should add the file to the appropriate layer's include array as part of the migration PR — that's how the empty scaffold turns real.
- The paperclip agent rewrites `apps/operator/app/harness/*` (not under `api/`, but adjacent). Routes under `api/harness/*` are safe from paperclip.
