Systems audit · 2 September 2026

Where inventory stops and file generation begins

Restart and storewolf-central-server are coupled at the data layer, not the service layer. The marketplace file pipeline never calls the inventory service — it reads the Mongo inventory collection directly, at three call sites through one ten-field projection. That is the whole seam, and it is why the split you want is cheap on the file-generation side and expensive on the other.

storewolf-central-server — Mongo, COM service bus, Node CJS Restart — Postgres, Drizzle, NestJS, shop.buyrestart.com the cut

01The finding that changes the answer

Read this before the plan — it reframes the size of the job

Load-bearing

Restart does not have an inventory management system. It has an inventory mirror. The inventory_item table has exactly one write path in the entire repository — TRUNCATE TABLE inventory_item followed by a batched INSERT of whatever storewolf's InventoryManager hands over (inventory.service.ts:27,37). The only other write anywhere is a single odooProductId write-back (inventory-sync.service.ts:216).

There is no receive, no adjust, no move, no reserve, no sell, no serial-scan path. Nothing in Restart can change what you own — it can only be told. So “move inventory management to Restart” is not a re-pointing exercise. The management half has to be built, and it is the large part of this project. Everything else here is small.

The good news is the inverse: because file generation reads the collection and not the service, the pipeline you want to keep does not care where the rows came from. You can move the system of record without the feed generator noticing, provided the rows keep their shape.

02What each side actually is

Verified against source, not documentation

Old · storewolf-central-server

The real system of record

Services/InventoryManager/ — 84 KB of TypeScript behind a 47-method COM interface. This is genuine warehouse operations: createSkuOrder, createBinOrder, updateSkuQuantity, sellOrderItemsForReserve, unsellOrders, associateScanData, getOrderFromSerial, updateInventoryLocations, reparseInventory.

Its store is the Mongo inventory collection, where one document is one physical unit — order id, service tags, location, leads, reserves, parsed specs.

New · Restart

A strong storefront, a hollow warehouse

65 Drizzle migrations. storefront_product is genuinely authoritative for selling: it owns qty, reserved_qty and price_cents directly, with availableQty as a GENERATED STORED column (GREATEST(0, qty - reserved_qty)) and database triggers aggregating reservations from order and quote lines (migration 0028).

inventory_item, by contrast, is a ~70-column replica of the Mongo document, refilled wholesale on each sync.

The pipeline you are keeping

MarketplaceStuff.generateUploads() is the file generator. It calls Synchronizer.generateUpdatesTwo to build the update list, reads it back out of DataStore by run id, joins it against series details, combined specs, marketplace report data and SKU specs, and writes per-marketplace upload files. Between the inventory read and the file sits the part that would be genuinely painful to reproduce:

  • stock reduction and custom-condition grading
  • lead association across site, dellcom and Amazon sources
  • listing generation, then pricing per marketplace
  • marketplace fee application, ad-cost markups, score markups
  • inferior-listing removal, zero-out of delisted SKUs, prior-SKU reconciliation

That is roughly 270 KB of pricing and listing logic across SyncPipeline.ts and Synchronizer.ts, and it is the reason keeping file generation where it is happens to be the right call and not merely the conservative one.

03The seam

Three call sites, ten fields, two queries

Live inventory read Site Mongo query Feeds
pipelineLoadLocalStock Synchronizer.ts:3889 status: active, items: $size 1, type ≠ sku Serialized single-unit stock
pipelineLoadLocalSkuStockFromInventory Synchronizer.ts:3921 status: active, type: sku BIN / multi-unit SKU stock
loadCustomConditionStock Synchronizer.ts:790 … + items.0.tag ∈ graded tags Manually graded condition stock

All three share INVENTORY_PROJECTION — ten fields, and no more: price, items, leads, reserves, location, specs.model, specs.family, specs.type, skuSpecs.category, skuSpecs.condition. Every one of them is then flattened by standardizeInventoryItem into a StandardItem and never touched again.

That is the entire contract the file-generation pipeline has with inventory. It is small enough to serve from anywhere.

04What is already wired, and what is broken

Current state of the bridge between the two systems

There are two bridges today. Both are half-built, and knowing that changes where you start.

Bridge Direction State Detail
updateFromExternal storewolf → Restart Works com('InventoryManager','loadActiveInventory',{locationFilter:'ELI-'}), then full-table replace. Hard-coded to one location prefix.
Restart.js updateToSite storewolf → Restart Disabled Builds the WEBSITE / US update list correctly, then the fetch is commented out — it writes updateToSite_body.json to disk instead. It also posts a bare array where the controller expects { records: [...] }, so it would 400 if simply uncommented.

The contract is already agreed, which is the useful part

Restart's updates table is a fully flattened relational mirror of storewolf's ProductUpdate wire format — including the pricing internals: sw_cost, sw_initial_min_price_markup, sw_score_markup, sw_marketplace_fee, the sw_tr_* transform block and the sw_asin_* median block, keyed by (sku, marketplace, region). Someone has already done the schema work to accept this pipeline's output verbatim. Do not redesign it.

Field gaps that will bite

Field needed by the pipeline In inventory_item? Consequence if missing
type Missing The sku / non-sku split is the entire difference between the two find-params. Without it you cannot separate BIN stock from serialized stock.
manualPrice Missing Custom-condition graded pricing silently drops to the default price path.
manual_handling Missing Handling-day banding (0 / 3 / 5 / 8) is lost; listings ship with wrong lag time.
specs Missing Projected as specs.model / family / type. Restart has parsedSpecs, skuSpecs, listSpecs, predictiveSpecs — confirm which one is the true equivalent before mapping.
price, items, leads, reserves, location, skuSpecs Present Direct column equivalents already exist.

05The migration

Ordered so that nothing is irreversible until the shadow run is clean

Phase 0

Repair the bridge and close the field gaps

Restore the fetch in Restart.js::updateToSite with the { records: [...] } envelope the controller actually expects. Add the four missing columns to inventory_item and resolve which Restart specs column is the real counterpart of Mongo's specs.

Touches Restart.js, one migration Risk low Reversible yes
Phase 1

Introduce the InventorySource port — behaviour unchanged

Extract the three direct db.collection('inventory').find(...) calls behind one interface with three methods: loadLocalStock(), loadSkuStock(), loadCustomConditionStock(tags). Ship the Mongo implementation as the only implementation and prove the generated update list is byte-identical to today's.

This phase changes no behaviour on purpose. It is what makes every later phase a one-line switch rather than a rewrite.

Touches Synchronizer.ts, SyncPipeline.ts Risk low Gate identical update list
Phase 2

Build the write side in Restart — the actual work

Of InventoryManager's 47 methods, most are reads, derivations and enrichment that can stay where they are indefinitely. What has to move is the stateful core: receive a unit, adjust quantity, sell, reserve and unsell, associate a serial or barcode scan, move a location, reparse. Roughly a dozen operations.

In the same phase, inventory_item stops being a mirror: drop the truncate-and-refill, add real upserts, and give it the audit trail a system of record needs. This is the phase that is measured in weeks, not days.

Touches new Restart module, schema, admin UI Risk high Gate parity on warehouse operations
Phase 3

Flip the source behind a shadow run

Add the Postgres implementation of the port — ideally a GET /inventory/stock-feed endpoint serving exactly the ten-field projection shape, so the pipeline keeps one transport rather than gaining a second database connection. Then run both implementations on every cycle and diff the resulting update lists per marketplace and region until the diff is empty.

Flip a config flag. The file generator is not modified in this phase, or in any phase.

Touches one config flag Risk medium Gate zero-diff shadow run
Phase 4

Retire the Mongo write path

The inventory collection becomes derived and read-only, then goes away. InventoryManager's write methods are removed; its read and enrichment methods either follow or stay, on their own schedule. Nothing here blocks anything.

Risk low once Phase 3 holds

06Two things to decide before Phase 2

Both are cheap now and expensive later

Decision 1

Port the reads, or reverse-replicate into Mongo?

The plan above ports the reads. The alternative is to make Restart authoritative and have it project rows back into the Mongo inventory collection, so storewolf reads exactly as it does today and Phase 1 and Phase 3 disappear entirely. That is meaningfully lower risk and keeps a second copy of inventory alive indefinitely — which is the thing this migration exists to end. Worth taking deliberately rather than by default.

Decision 2

What happens to libs/marketplace-adapters?

Restart already contains a second, independently built marketplace mapping layer — Amazon, eBay, Walmart, Newegg, Back Market, Best Buy Canada and Google Shopping, each with its own computer-category mapping. If file generation stays on MarketplaceStuff, this library is a fork of listing truth that will drift. Freeze it, scope it explicitly to something MarketplaceStuff does not do, or delete it — but do not leave two systems quietly disagreeing about how a SKU becomes a listing.
